## 0. 执行摘要

### 0.1 一句话定义

**PluginHub**（暂定名）是一个本地优先的运行时控制台，负责把散落在各种协议、各种客户端里的 AI 插件和 Agent **统一发现、自动拉起、安全治理、智能调度**——解决"协议只管怎么调用，不管怎么运行"的系统性空白。

### 0.2 核心价值主张

| 痛点（来自竞品报告 §2.6） | PluginHub 的解法 |
|---|---|
| 安装配置繁琐、静默失败 | Manifest 声明式 + 运行时二次校验 + 显式错误上报 |
| 端口冲突需手工排查 | bind(0) + fd 传递，零 TOCTOU |
| 崩溃无恢复 | 声明式 restartPolicy + CrashLoopBackOff + 状态检查点 |
| 重复进程破坏共享状态 | 单例守护进程 + 会话级进程隔离 |
| 工具命名冲突静默丢弃 | 全局名称注册表 + 前缀策略 + 冲突检测告警 |
| Agent 元数据不统一 | 统一能力模型 Canonical Capability + 多协议适配器 |
| 跨 Agent 观测断裂 | OTel traceparent 透传 + Task.id 关联 + 统一事件总线 |
| 日志分散、错误晦涩 | stdio 管道 → JSONL → SQLite + SSE viewer |

### 0.3 三个差异化护城河

1. **跨协议统一运行时层**：MCP/A2A/Skills/OpenAPI/Arazzo 归一为 Canonical Capability，且保留 `provenance.native` 原文
2. **声明式进程生命周期**：Manifest 中补齐所有协议缺失的 runtime 段（启停/健康/端口/资源/沙箱），由编排内核执行
3. **安全治理四层叠加**：权限默认拒绝 + 信任三态分离 + 沙箱隔离 + 审批门

### 0.4 明确不做的事

| 不做 | 原因 |
|---|---|
| 低代码画布 | Flowise EOL 已证伪该路线 |
| 自研传输协议 | 传输层已收敛到 stdio/Streamable HTTP/gRPC |
| 纯注册表/托管服务 | Smithery/mcp.run 关停证明此模式不成立 |
| 把 A2A Agent 伪装成 MCP Tool | 丢失人工介入语义 |
| 全量暴露 OpenAPI 为工具 | 上下文爆炸 + 路由错误率上升 |
| 依赖单一 well-known 路径 | 渗透率仅 1.7%–5.8%，必须三路并行 |

### 1.2 核心设计原则

| 原则 | 具体做法 | 来源 |
|---|---|---|
| **只放指针，不复制内容** | Manifest 的 components 段只存路径/URL；SKILL.md、mcp.json、agent-card.json 保持原生格式权威 | 协议报告 §7.1 |
| **顶层 closed，扩展 open** | 未知顶层字段报错；extensions 内按反向域名命名空间开放 | 协议报告 §7.1 |
| **失败隔离** | 清单错→整包拒；组件错→跳该组件；运行期错→降级该能力 | 协议报告 §7.4 |
| **权限默认拒绝** | permissions 缺省为"无权限"，不是"全权限" | 协议报告 §7.1 |
| **信任三态分离** | signed / verified / trusted 不得合并 | 协议报告 §2.2.3 |
| **进程生命周期借鉴 MCP SDK** | 有界等待 + shield 关停序列 | 进程报告 §9.3 |
| **动态端口零 TOCTOU** | bind(0) + fd 传递，env PORT 兜底 | 进程报告 §5.2 |
| **日志走 stdio 管道** | 不走文件 tail，绕开 rotation/inode/Windows 痛点 | 进程报告 §7.1 |
| **可降级导出** | 能无损导出为 Agent Plugins / Claude Code / MCP server.json / A2A Agent Card | 协议报告 §7.5 |

## 2. 模块详细设计

### 2.1 Discovery Engine（发现引擎）

**职责**：从多个来源收集插件/Agent 描述，去重、评分、写入统一索引。

#### 2.1.1 四路并行发现

| 优先级 | 来源 | 触发条件 | 说明 |
|---|---|---|---|
| P0 | 本地已安装清单 + 用户显式配置 | 启动时 | 最快、最可信 |
| P1 | `/.well-known/ai-catalog.json` | 用户添加域名时 | 一次拿到该域名下全部能力 |
| P2 | 各协议卡片探测列表（并行） | P1 无结果时 | mcp/server-card → mcp.json → agent-card.json → agent.json |
| P3 | Registry 查询 | 用户主动搜索时 | MCP Registry / AGNTCY DIR / ClawHub |
| P4 | 本地目录扫描 | 后台定时 | `~/.pluginhub/plugins/`、项目 `.plugins/` |

**现实兜底**：因 well-known 渗透率仅 1.7%–5.8%，对已知主机默认 POST `/mcp` + `server/discover`（MCP 2026-07-28 MUST），能应答即认定为 MCP server。

#### 2.1.2 去重与优先级

- **去重键**：`(publisher.domain, metadata.id)`
- **择一规则**：trust 等级 > 版本号 > 显式配置 > 最近更新时间
- **其余来源记为 mirrors**，供故障切换
- **缓存**：严格遵守 MCP `ttlMs` / `cacheScope`；`private` 结果不入共享缓存

#### 2.1.3 工具名冲突检测

- 全局名称注册表维护 `(toolName → capabilityId)` 映射
- 新注册时检查冲突，冲突则：
  - 若同 pluginId → 报错
  - 若不同 pluginId → 自动加 `routing.context.toolNamePrefix`，并告警用户
- 解决竞品报告痛点 5（同名工具静默丢弃）

### 2.2 Activation Engine（激活引擎）

**职责**：解析清单 → 安装/定位 → 权限求解 → 信任求解 → 拉起进程 → 健康检查 → 注册到可调度池。

#### 2.2.1 加载流水线

```
读清单 → JSON Schema 校验 → apiVersion 判别 → 逐组件解析
  → 权限求解（未授予 → unavailable）→ 信任求解（三态）
  → 按 activation 策略决定是否立即拉起
  → health probe 通过 → 进入可调度池
```

#### 2.2.2 激活策略

| 策略 | 行为 | 适用 |
|---|---|---|
| `eager` | 启动即拉起 | 核心基础设施插件 |
| `lazy` | 首次被调度时拉起 | 大多数插件（省资源） |
| `on-demand-by-agent` | 指定 Agent 请求时拉起 | Agent 专属工具 |
| `manual` | 仅手动触发 | 危险/调试工具 |

#### 2.2.3 信任求解（三态）

| 状态 | 条件 | 默认行为 |
|---|---|---|
| `self-asserted` | 未签名 | 要求用户显式确认 |
| `verified-untrusted` | 验签通过但 key 未 pin | 允许使用但标记警告 |
| `trusted` | key 来自已信任 JWKS/DID/OIDC | 正常使用 |

**关键约束**：禁止 HS256 对称签名；验签时必须传显式算法白名单。

### 2.3 Process Orchestrator（进程编排内核）

**职责**：管理所有插件子进程的生命周期。

> 本模块完整复用进程报告的选型结论，此处仅列架构要点，实现细节见进程报告。

#### 2.3.1 技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | Go | 单静态二进制、交叉编译最简单 |
| 进程启动 | `os/exec` + `SysProcAttr{Setpgid}` / Job Object | 标准库覆盖 |
| 生命周期协议 | 借鉴 MCP Python SDK `stdio.py` | 全清单最可靠参考 |
| 动态端口 | bind(0) + SCM_RIGHTS / WSADuplicateSocket | 零 TOCTOU |
| 健康检查 | HTTP `/healthz` > TCP > gRPC health | K8s 参数 + 抖动 |
| 优雅关闭 | SIGTERM/CTRL_BREAK → grace → SIGKILL/TerminateJobObject | 跨平台统一 |
| 日志 | stdio 并发 drain → bufio.Scanner → slog JSONL → SQLite + SSE | 无外部依赖 |
| 服务模式 | 前台进程 + systemd/launchd/SCM 托管 | 三平台一套逻辑 |

#### 2.3.2 进程状态机

```
CREATED → STARTING → READY → RUNNING → STOPPING → STOPPED
                ↑                    ↓
                └── RESTARTING ← FAILED
```

- `READY` = health probe 连续 successThreshold 次通过
- `FAILED` = failureThreshold 次失败 或 startTimeout 超时
- `RESTARTING` = 按 CrashLoopBackOff 退避（1s × 2^n，上限 60s，full jitter）

#### 2.3.3 会话级进程隔离

- 每个 Agent 会话可拥有独立的插件进程实例（解决竞品报告痛点 4）
- 进程实例绑定 session ID，取消会话时确定性回收
- 共享插件（如只读 MCP server）可跨会话复用，由 `concurrency.maxParallel` 控制

### 2.4 Invocation Router（调度路由器）

**职责**：接收 Agent/用户的意图，匹配最佳能力，执行审批门，分发到对应适配器。

#### 2.4.1 调度流水线

```
意图输入 → 语义匹配（examples + representativeQueries）
  → 候选排序（trust > costHint > latencyHint）
  → 权限检查 → 审批门（requiresApproval/destructive）
  → 适配器调用 → 结果归一 → 事件上报
```

#### 2.4.2 意图匹配策略

| 匹配方式 | 数据来源 | 精度 | 成本 |
|---|---|---|---|
| 精确绑定 | `capabilityRefs` | 最高 | 零 |
| 示例匹配 | `routing.intents[].examples` | 高 | 低（向量/关键词） |
| 语义检索 | OASF 分类 + description | 中 | 中（embedding） |
| LLM 路由 | 工具描述注入 prompt | 灵活 | 高（token） |

**两阶段注入**：先给 name+summary（~20 token/工具），命中后再拉完整 schema，控制上下文预算。

#### 2.4.3 审批门

| 触发条件 | 行为 |
|---|---|
| `requiresApproval: true` | 暂停执行，推送确认请求给用户 |
| `destructive: true` | 强制 requiresApproval + 二次确认 + 审计日志 |
| 权限未授予 | 返回 `unauthorized`，提示用户授权 |
| 超出 quota/budget | 返回 `rate_limited`，提示配额耗尽 |

### 2.5 Observer Bus（观测总线）

**职责**：统一采集运行时事件，串联跨 Agent/跨协议的 trace。

#### 2.5.1 事件类型

| 事件 | 来源 | 关键字段 |
|---|---|---|
| `capability.invoked` | Router | capabilityId, protocol, latency, outcome |
| `process.state_changed` | Orchestrator | pid, oldState, newState, reason |
| `health.probe_result` | Orchestrator | target, result, duration |
| `permission.requested/granted/denied` | Activation | pluginId, permissionId, decision |
| `trust.verification` | Activation | pluginId, status, algorithm, keyId |
| `error.unified` | 全链路 | unifiedCode, nativeError, stackTrace |

#### 2.5.2 Trace 串联

- MCP 调用：复用 `_meta.traceparent` / `tracestate`（2026-07-28 已文档化）
- A2A 调用：`Task.id` + `contextId` 做跨 hop 关联
- 内部调用：生成 spanId，注入下游
- 所有事件写入 SQLite `events` 表 + SSE 推流

#### 2.5.3 日志 Viewer

- **主路径**：SSE Web viewer（Control UI 内嵌）
- **调试**：`tee` 给 lnav / Logdy
- **查询**：SQLite `SELECT * FROM logs WHERE run_id=? AND level>=? ORDER BY ts`

### 2.6 Unified Capability Index（统一能力索引）

**存储**：SQLite 单文件，零运维。

#### 2.6.1 核心表结构

```sql
-- 插件注册表
CREATE TABLE plugins (
  id TEXT PRIMARY KEY,           -- com.acme.deploy-assistant
  version TEXT NOT NULL,
  manifest_path TEXT NOT NULL,
  trust_status TEXT NOT NULL,    -- self-asserted | verified-untrusted | trusted
  activated_at TEXT,
  health_status TEXT,            -- healthy | unhealthy | unknown
  process_pid INTEGER,
  assigned_port INTEGER
);

-- 统一能力索引
CREATE TABLE capabilities (
  id TEXT PRIMARY KEY,           -- pluginId/componentId/member
  plugin_id TEXT NOT NULL REFERENCES plugins(id),
  kind TEXT NOT NULL,            -- tool | skill | agent | workflow | resource | app
  display_name TEXT,
  summary TEXT,
  input_schema TEXT,             -- JSON
  output_schema TEXT,            -- JSON
  semantics_json TEXT,           -- {readOnly, destructive, idempotent, openWorld}
  protocol TEXT NOT NULL,        -- mcp | a2a | skills | openapi | arazzo
  native_json TEXT NOT NULL,     -- 原始描述对象，原样保留
  examples_json TEXT,            -- ["把这个服务发到预发"]
  cost_hint TEXT,
  requires_approval BOOLEAN DEFAULT FALSE
);

-- 运行时事件
CREATE TABLE events (
  ts TEXT NOT NULL,
  type TEXT NOT NULL,
  payload_json TEXT NOT NULL,
  trace_id TEXT,
  span_id TEXT
);

-- 结构化日志
CREATE TABLE logs (
  ts TEXT NOT NULL,
  run_id TEXT NOT NULL,
  stream TEXT NOT NULL,          -- stdout | stderr
  level TEXT NOT NULL,
  msg TEXT NOT NULL,
  attrs_json TEXT
);

-- 权限授予记录
CREATE TABLE permissions_granted (
  plugin_id TEXT NOT NULL,
  permission_id TEXT NOT NULL,
  granted_at TEXT NOT NULL,
  granted_by TEXT NOT NULL,      -- user | policy
  expires_at TEXT
);
```

#### 2.6.2 索引策略

- `capabilities(kind, protocol)` — 按类型/协议过滤
- `capabilities(plugin_id)` — 按插件聚合
- `events(trace_id)` — trace 查询
- `logs(run_id, ts)` — 日志时间窗查询

## 3. Plugin Manifest 规范（核心资产）

> 完整 Schema 草案见协议报告 §7。此处仅列架构相关的关键设计决策。

### 3.1 七段结构

| 段 | 职责 | 必填 |
|---|---|---|
| `metadata` | 身份、版本、发布者 | ✅ name + version |
| `discovery` | well-known 路径、registry 条目、mediaTypes | ❌ |
| `components` | 技能/MCP/OpenAPI/Agent/Workflow/App 的指针 | ✅ 至少一个 |
| `runtime` | 入口、激活策略、健康检查、生命周期、资源、沙箱 | ❌（无则视为 hosted-only） |
| `permissions` | fs/net/exec/secrets/artifact 权限声明 | ❌（缺省=无权限） |
| `trust` | 签名、完整性、来源、发布者验证 | ❌（缺省=self-asserted） |
| `routing` | 意图示例、能力引用、触发器、并发、上下文预算 | ❌ |

### 3.2 跨字段强约束（写进 Schema）

| 约束 | 理由 |
|---|---|
| `trust.signing.algorithm != "HS256"` | 对称签名对公开清单无意义 |
| `permissions.hosts[] ⊆ runtime.sandbox.network.egress` | 沙箱与权限不得矛盾 |
| `routing.intents[].capabilityRefs` 必须在 components 中可解析 | 防悬空引用 |
| `destructive == true ⇒ requiresApproval == true` | 破坏性操作强制审批 |
| `components.openapi[].operations` 非空 | 禁止全量暴露 |
| `extensions` key 必须匹配反向域名正则 | 防命名空间抢占 |

### 3.3 可降级导出矩阵

| 目标格式 | 保留 | 丢失 |
|---|---|---|
| Agent Plugins 1.0 | skills + mcp.json + metadata 子集 | routing / permissions / trust / lifecycle |
| Claude Code plugin | skills + mcp + commands | 同上 + userConfig 需另映射 |
| MCP server.json | name + version + packages/remotes | 技能、工作流、Agent、权限 |
| A2A Agent Card | name/description/version/skills/capabilities | 工具级 schema、权限、路由预算 |
| AI Catalog 条目 | id/displayName/mediaType/url/tags/representativeQueries | 除索引信息外全部 |

## 4. 协议适配层设计

### 4.1 适配器职责边界

| 适配器 | 输入 | 输出 Canonical Capability | 红线 |
|---|---|---|---|
| MCP ToolAdapter | `tools/list` + annotations | kind:tool + 语义四元组 | 不得自动重试 destructive |
| OpenAPI ToolAdapter | 白名单 operationId | 三元工具 (list/get-schema/invoke) | 不得全量导入 |
| A2A AgentAdapter | AgentCard + Task 生命周期 | kind:agent, mode:task | 不得伪装成同步工具 |
| Skills InstructionAdapter | SKILL.md frontmatter | kind:skill, 仅 name+description | discovery 阶段不读正文 |
| Arazzo WorkflowAdapter | flow 定义 | 单个 kind:workflow | 不把每 step 提升为独立工具 |
| OASF RegistryAdapter | OASF 记录 | 能力标签 + 分类 ID | 不当可执行能力 |

### 4.2 统一错误模型

| 统一码 | MCP | HTTP | A2A |
|---|---|---|---|
| `not_found` | -32601 | 404 | REJECTED |
| `invalid_input` | -32602 | 400/422 | — |
| `unauthorized` | -32021 | 401/403 | AUTH_REQUIRED |
| `rate_limited` | — | 429 (+Retry-After) | — |
| `unavailable` | -32022 / 连接失败 | 5xx | FAILED (infra) |
| `interrupted` | 流中断 | — | CANCELED |
| `internal` | -32603 | 5xx | FAILED (logic) |

**规则**：统一码用于路由/重试；原始错误必须透传给日志与审计。

### 4.3 能力降级矩阵

| 缺失 | 降级 | 影响 |
|---|---|---|
| streaming | 轮询 GetTask（≥2s 指数退避） | 进度延迟 |
| pushNotifications | 本地轮询 + 完成回调 | 长任务无法即时感知 |
| outputSchema | 文本 + 启发式解析 | 结构化下降 |
| inputSchema (A2A) | examples + inputModes 构造松散参数 | 错误率上升，需人工确认 |
| MCP Apps | structuredContent + 文本 | UI 消失功能保留 |
| 仅 SSE | 桥接 Streamable HTTP | Last-Event-ID 语义丢失 |
| 无会话 (2026-07-28) | 服务端句柄作普通参数 | 需插件配合 |

## 5. 安全架构

### 5.1 四层防御

```
┌─ Layer 1: 权限默认拒绝 ─────────────────────────────────┐
│  permissions 缺省=无权限；未授予的能力标记 unavailable     │
├─ Layer 2: 信任三态分离 ─────────────────────────────────┤
│  self-asserted → 显式确认                                 │
│  verified-untrusted → 警告但允许                          │
│  trusted → 正常使用                                       │
├─ Layer 3: 沙箱隔离 ─────────────────────────────────────┤
│  filesystem: read/write 白名单                            │
│  network: egress 域名白名单                               │
│  exec: command 白名单                                     │
│  secrets: 只允许 refs，broker 注入                        │
├─ Layer 4: 审批门 ───────────────────────────────────────┤
│  destructive → 强制二次确认 + 审计                        │
│  requiresApproval → 暂停等用户确认                        │
│  权限变更 → rug pull 检测 + 重新审批                      │
└──────────────────────────────────────────────────────────┘
```

### 5.2 威胁对策表

| 威胁 | 对策 |
|---|---|
| 工具描述投毒 | 描述按不可信输入处理，不拼接进系统提示 |
| Rug pull | listChanged 通知 + 工具定义哈希基线 |
| 签名伪造 | 强制非对称 + 显式算法白名单 |
| 密钥泄漏 | 只允许 refs；header isSecret 校验 |
| 路径逃逸 | realpath 后必须在 PLUGIN_ROOT 内 |
| UI 注入 | 沙箱 iframe + CSP default-src 'none' + 模板预审 |
| 供应链攻击 | integrity.digest + SLSA provenance + 允许列表 registry |
| 权限蔓延 | 最小集审批 + 运行期越权阻断 |

### 7.2 风险登记

### 7.3 Fork 决策门（P5 末）

若 P0–P4 自研成本显著高于 fork `process-compose` + 改造成本，则切换：
- 移植动态端口自动分配
- 补充结构化事件流
- 增加会话级进程隔离
- 评估标准：同一组端到端用例的通过率与代码行数比
