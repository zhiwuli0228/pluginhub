# 本地进程编排与动态端口管理技术选型决策文档

> 面向 `Process Orchestrator` 模块：在本地（Windows / macOS / Linux）启动、监管、回收一批子进程（典型为 AI agent worker、MCP stdio server、sidecar），要求可靠、跨平台、轻量，并避免重复造轮子。
>
> 版本 v1.0 · 2026-11-20 · 调研核实窗口 2026-11-19 ~ 2026-11-20

---

## 0. 阅读须知：可信度分级与口径警告

沿用本工作区既有深度研究报告的 A/B/C/D 分级：

| 级别 | 含义 | 本文档中的典型来源 |
|---|---|---|
| **A** | 官方一手：官方文档 / 官方仓库 README / LICENSE / 官方源码 / GitHub API 原值 / 内核 man-page / RFC | nodejs.org、pkg.go.dev、kernel.org、RFC 6335、Microsoft Learn、各项目官方仓库 |
| **B** | 官方自报或第三方一手但非本场景：库自带 benchmark、厂商自测、他人仓库的实测 | pino/zap/zerolog 自报基准、`yq-core` 自报 CLI 基准 |
| **C** | 经验量级 / 合理推断：无统一官方基准，给出数量级并标注"经验值" | 冷启动、idle RSS、二进制体积量级 |
| **D** | 存疑 / 未核实：本轮未能一手确认，或信息污染严重 | star 数、macOS/Windows TIME_WAIT 精确值、部分库许可证细节 |

**口径警告（务必先读）：**

1. **没有任何可信的"三语言进程管理统一基准"**。凡是给出"Node 比 Go 慢 N 倍"这类精确数字的文章，本轮核查后均判定为 SEO 污染（如 johal.in 一类站点出现自相矛盾的"Rust 2.0 / Clap 5.0 / 1.2ms"），**一律不采信**。启动/RSS/体积只给经验量级（C 级）。
2. **star 数不作选型依据**。GitHub API 与多个第三方站对同一仓库给出差异巨大的 star 值（本项目此前已发现 claude-mem 在 4 个来源为 46K/90.1K/100.3K/103.9K）。用 **README / LICENSE / 最近 commit 三件套**判断活跃度与可用性。
3. **许可证以仓库内 LICENSE 文本为准**，GitHub API 的 `license` 字段常返回 `NOASSERTION`（pm2 / supervisor / s6-overlay 均如此）。
4. **信息时效**：Node 文档抓取显示 v26.13.1，Go / Rust / 各库版本随时间变化；signal 在 Windows 的文档措辞 v18 与 v24 不同但行为结论一致（强制终止）。凡版本敏感处均标注"目标版本需实测"。

## 1. 执行摘要

**一句话结论：** 用 **Go 自研一层薄编排内核**，`os/exec` + `SysProcAttr{Setpgid}`（Unix）/ Job Object（Windows）解决进程生命周期，`bind(port 0)` + fd 传递解决动态端口，HTTP/TCP probe + `SIGTERM→宽限→SIGKILL` 解决健康检查与优雅关闭，stdio 管道 + JSONL + SQLite/SSE 解决日志；**进程生命周期协议直接借鉴 MCP Python SDK 的 `stdio.py`（A 级参考实现）**，不重复造"如何正确 spawn/关停一个子进程"的轮子；只在需要"现成编排器 + AI 控制面"时才考虑 fork `process-compose`（Apache-2.0）。

### 1.1 七个关键判断

| # | 判断 | 级别 |
|---|---|---|
| 1 | 三语言原生都**没有可移植的"进程树杀死 + 退出兜底回收"**。Go / Rust 必须自己写（Unix 进程组 + Windows Job Object）；Node 可用 `execa` 的 `killDescendants` 补齐（best-effort）。这是本模块唯一真正要造的轮子。 | A |
| 2 | 默认推荐 **Go**：单静态二进制、`GOOS/GOARCH` 交叉编译最简单、`os/exec` 已覆盖 spawn/stdio/context 取消。Node 胜在生态与开发速度但 runtime 开销与 SEA 分发限制明显；Rust 运行时最优但 TCO 最高。 | A/C |
| 3 | 动态端口**首选 OS 分配（`bind` port 0）+ 传已 bind 的 fd**，从根上消除 TOCTOU；端口池和 mDNS 对单机本地场景是过度设计。环境变量传端口可作兜底。 | A |
| 4 | Windows 的**保留端口**（Hyper-V/WSL2/Docker 动态 reserve）和 Linux 的 **ip_local_port_range=32768-60999** 决定了"硬编码端口段最易踩雷"，进一步支持"让内核分配"路线。 | A |
| 5 | 健康检查用 **HTTP `/healthz`** 优先、TCP 次之、gRPC 服务用 `grpc.health.v1`；参数以 K8s 默认值为起点并按本地低延迟收紧；**探测/重启加抖动**防 thundering herd。 | A |
| 6 | 编排器既然持有子进程 stdout/stderr 管道，**就根本不需要文件 tail**——tail 的 rotation/inode 痛点、Windows 无原生 tail 等问题全部绕开。文件 tail 仅作"接管外部已有日志"的可选 fallback。 | A |
| 7 | 真正"AI-aware 的本地进程管理器"是存在的：MCP 官方 SDK 的 stdio transport 就是其现实答案；`process-compose`（内置 MCP server）、`mcpmu`、`mcp-sidecar` 是可复用/可 fork 的候选，不必从零设计。 | A |

### 1.2 决策矩阵速览

| 决策点 | 推荐 | 备选 | 明确不推荐 |
|---|---|---|---|
| 主语言 | Go | Node + execa（worker 全是 Node/TS 时） | Rust（除非体积/内存硬约束） |
| 编排底座 | 自研薄层 + 借鉴 MCP Python SDK `stdio.py` | fork `process-compose` | pm2 / supervisor 作底座 |
| 动态端口 | bind(0) + fd 传递 | 端口池（需固定端口时） | mDNS（单机场景）；connect 探测 |
| 健康检查 | HTTP `/healthz` | TCP / gRPC health | 无超时 probe |
| 进程树关停 | Unix 进程组 + Windows Job Object | `taskkill /T /F`（降级） | 只发 SIGTERM 给直接子进程 |
| 日志 | stdio 管道 + JSONL + SQLite/SSE | 文件 tail（外部进程） | `spawn('tail')`（Windows 不可用） |
| 服务模式 | 前台进程 + systemd/launchd/SCM 托管 | 自安装服务适配层 | 依赖终端 SIGHUP 做清理 |

## 2. 需求定义与边界

先把"这个模块是什么 / 不是什么"说清楚，否则选型容易跑偏：

| 维度 | 本模块（Process Orchestrator） | 传统进程管理器（pm2/supervisord） |
|---|---|---|
| 管理对象 | 短命、数量动态、由工具调用触发的 worker / MCP stdio server | 长驻应用、服务 |
| 生命周期 | 一次调用 = `spawn → ready → call → teardown`，进程可被随时取消 | 常驻 + 崩溃自动拉起 |
| 端口 | 运行时动态分配并回填给调用方（LLM / 上层） | 配置写死或 `$PORT` 注入 |
| 输出 | 结构化事件流（JSON-RPC / JSONL），供 LLM 消费 | 文本日志 |
| 权限 | 可执行白名单、命令黑名单、审计、工具级 allow/deny | 假设命令可信配置 |
| 隔离 | 与工具调用生命周期绑定；取消必须能清理进程且不被取消本身打断 | 无"调用"概念 |

**边界结论**：通用 PM 的设计假设与本模块几乎相反，因此**不以 pm2/supervisor 为底座**；真正要借鉴的是 MCP SDK 的 stdio 生命周期协议（见 §10）。

## 3. 语言 / 运行时选型：Node.js / Go / Rust

### 3.1 子进程原语能力对比（A 级：官方文档）

| 能力 | Node.js `child_process` | Go `os/exec` | Rust `std::process` / `tokio::process` |
|---|---|---|---|
| 启动 | `spawn/exec/execFile/fork`；默认无 shell | `exec.Command` + `Start/Run/Wait` | `Command::spawn/output/status` |
| IPC | `fork()` 内建 channel（stdio 需一个 `'ipc'`） | 无内建，需自行 pipe/socket | 无内建 |
| 进程组 / detached | `detached:true`（POSIX 新进程组 + session leader；Windows 独立 console 且父退后可活） | 需 `SysProcAttr{Setpgid}`（Unix-only） | 无可移植进程组 API |
| kill | `kill(signal)` 默认 SIGTERM，**只杀直接子进程**；Windows 全部信号按强制终止处理 | `Process.Kill()/Signal()` + `CommandContext` + `WaitDelay` | `kill_on_drop`；Unix runtime best-effort reap |
| stdio | pipe/inherit/ignore/ipc/fd；官方警告管道容量有限、不消费会阻塞 | `io.Reader/Writer`；非 `*os.File` 时 `Wait` 等拷贝协程 | 官方警告管道填满且不并发读会死锁 |
| 树形杀死 | 需 execa `killDescendants` 或自建进程组 | 自建（Unix 进程组 / Windows Job Object） | 自建 crate 组合 |

**核心事实**：四者原生都没有可移植的树形杀死。差异只在"补齐它要写多少代码"——Node 可由 execa 补齐，Go/Rust 要自己写平台抽象。

### 3.2 性能与体积（C 级：经验量级，非官方统一基准）

| 指标（经验量级） | Go / Rust 原生二进制 | Node.js 进程 |
|---|---|---|
| 冷启动 | ~1–15 ms | ~20–60 ms（含 V8 初始化） |
| idle RSS | ~2–15 MB | ~30–60 MB |
| 单实例成本 | 单进程 | 每 worker 一个 V8；`fork()` 文档明确警告"不建议大量 spawning Node 子进程" |

**唯一可核验的自报数据（B 级，第三方非本场景）**：crates.io `yq-core 0.1.3` README 自报（11 次串行、2 次预热、`/usr/bin/time -l` 中位数）：CLI 启动 Go 8.7ms / Rust native 3.9ms / npm(Node) 38.1ms；1KB 输入 peak RSS Go 14.3MiB / Rust 2.5MiB / Node 41.5MiB。**YAML CLI 工作负载，不可外推到编排器。**

### 3.3 打包与分发（A 级）

| 语言 | 机制 | 典型体积（C 级） | 交叉编译难度 |
|---|---|---|---|
| Go | 单静态二进制；`GOOS/GOARCH` 即可 | ~2–10 MB | **最低** |
| Rust | 单二进制 + musl 静态（musl 细节本轮 404 未核实 → D 级） | ~0.5–5 MB | 中（需 `rustup target add` + 链接器） |
| Node | 官方 SEA（v19.7/v18.16 引入，Stability 1.1；v25.5 起 `--build-sea`）；`pkg` 已 archived，`nexe` 仍活跃；Bun `bun build --compile` 支持多目标 | node 二进制 + blob，数十 MB | 高（SEA 有 VFS 只读 / native addon 落临时文件 / `useCodeCache` 跨平台需关闭等限制） |

### 3.4 总拥有成本判断

- **Go（推荐）**：交叉编译与单文件分发碾压，标准库够用；唯一自研成本是进程组 / Job Object 抽象——而这恰恰是本模块无法回避的核心能力，早写早收益。
- **Node + execa（备选）**：若上游 worker 全是 Node/TS，开发速度最快，`killDescendants` 省掉部分轮子；代价是 runtime 开销、SEA 分发限制、守护语义缺失。
- **Rust（特定场景）**：运行时占用与安全最优，但异步 borrow、非可移植进程 API、编译时长推高 TCO；仅在体积/内存是硬约束时选。

### 4.2 易踩坑细节（A 级）

- **execa 树形杀死准确语义**：默认只发信号给直接子进程；`killDescendants:true` 才杀整棵树。Unix 上通过放入独立进程组实现，**自行 `setsid()` 的 daemon 会逃脱**；Windows 用 `taskkill`，明确标注 best-effort。父退出时默认 cleanup，但 `cleanup:false` / `detached` / 父被 SIGKILL 三种情况例外。选项名是 **`forceKillAfterDelay`**（不是 `forceKillAfterTimeout`）。
- **pm2 作为库嵌入**：`connect` 默认 spawn/connect 到本地 daemon，`disconnect` 后 daemon 与应用继续运行；全局 daemon 单例冲突风险（可用 `independent`/`custom` 缓解）。
- **`SO_REUSEPORT` 不是"把端口交给子进程"的工具**：它做多 socket 负载均衡（Linux 3.9+，要求 bind 前都设置且同 eUID），语义是共享 accept，不是转移所有权。用它规避 TOCTOU 属误用。
- **不要"先探测端口空闲 → close → 再 bind"**：经典 TOCTOU，正确做法是直接尝试 bind 并检查 `EADDRINUSE`。

## 5. 动态端口分配

### 5.1 三路线对比

| 路线 | 机制 | 竞态 / 可靠性 | 跨平台一致性 | 适用 |
|---|---|---|---|---|
| **A. OS 分配（bind port 0）** | 内核从 ephemeral range 挑端口，`getsockname()` 取回 | **无 TOCTOU**（内核原子分配并持有）；传已 bind fd 最稳 | 差：范围/回收各 OS 不同，fd 传递 API 不同 | ✅ 本项目推荐 |
| **B. 端口池 + 租约** | 预留端口段租给子进程，退出回收 | 探测与占用分离必有 TOCTOU；租约需心跳 + 过期回收 | 中 | 需固定/可预测端口、防火墙白名单 |
| **C. mDNS/Bonjour** | 组播 DNS-SD 广播服务名→端口 | 组播不可靠、发现延迟 | 差：Linux=Avahi（未移植 Windows）、macOS=Built-in、Windows 需 Bonjour SDK | 跨机器/局域网站点；**单机过度设计** |

### 5.2 推荐方案：bind(0) + fd 传递

```
父进程：fd = socket(); bind(fd, loopback:0); listen(fd);
        port = getsockname(fd).port;          // 内核已原子分配
        把 fd 交给子进程（下面两条路），端口所有权始终不释放 → 零 TOCTOU
```

**两种交法：**

1. **传已 bind 的 fd 本身（首选，零 TOCTOU）**
   - Linux/macOS/BSD：fork 时 fd 自动继承；运行时用 `SCM_RIGHTS` 经 AF_UNIX socket 发送（`unix(7)`：传的是对 open file description 的引用，语义等价 `dup` 到另一进程；Linux `SCM_MAX_FD=253`）。配合 `FD_CLOEXEC`。
   - Windows：`WSADuplicateSocket()` 生成 `WSAPROTOCOL_INFO` 经 IPC 传给子进程，子进程 `WSASocket()` 重建（每次只能被目标用一次；所有重复描述符 closesocket 后才真正关闭；flags 必须一致）；或 `CreateProcess` 设 `bInheritHandLES=TRUE`。
2. **仅传端口号（兜底，有 TOCTOU）**：环境变量 `PORT=<port>` 或 stdout 上报。端口从父释放到子 bind 之间可能被抢。用于子进程技术栈不便接收 fd 时（如某些托管运行时）。

### 5.3 三平台 ephemeral 端口范围（A 级，含存疑标注）

| OS | 默认 ephemeral 范围 | 查看/修改 | TIME_WAIT / 坑 |
|---|---|---|---|
| Linux | **32768–60999**（现代内核） | `/proc/sys/net/ipv4/ip_local_port_range`；`ip_local_reserved_ports` | `tcp_fin_timeout` 默认 60s；`tcp_tw_reuse` 默认 2（仅 loopback） |
| macOS | **49152–65535**（16383 个） | `sysctl net.inet.ip.portrange.first/last` | ⚠️ ~30s 为第三方说法，非 Apple 官方一手（D 级） |
| Windows | **49152–65535**（Vista/2008+） | `netsh int ipv4 show/set dynamicport tcp` | ⚠️ `TcpTimedWaitDelay` 默认 240s 本轮未一手核实（D 级）；**Hyper-V/WSL2/Docker 动态 reserve 大段端口**，`netstat` 看不到但 bind 失败，`netsh int ipv4 show excludedportrange protocol=tcp` 可见 |

> RFC 6335 §6：System 0–1023 / User 1024–49151 / Dynamic 49152–65535（"never assigned"，MUST NOT 作服务标识）。Linux 实际默认 32768 起落在 IANA Registered 段，属历史遗留。**Windows 保留端口坑最打击硬编码端口段，恰好被 bind(0)+fd 路线绕开。**

### 5.4 端口池与 mDNS 的具体不建议理由

- 端口池只在"必须稳定端口"（外部防火墙/配置依赖）时才值得；探测只能当 hint，真正可靠的只有"直接 bind，失败重试下一个"。
- mDNS 解决"我不知道对端在哪台机器/什么端口"；本地单机父进程亲自拉起子进程，天然知道 PID 和端口 → fd / 环境变量更可靠、零延迟、零依赖。仅当未来支持"外部进程独立启动后自动接入"再引入。

## 6. 健康检查与优雅关闭

### 6.1 三种 probe（A 级）

| Probe | 机制 | 成本 | 适用 |
|---|---|---|---|
| HTTP | `GET /healthz`，2xx–3xx 健康（K8s：≥200 且 <400） | 中，可携带依赖状态 | Web/API 服务，**本地调试最容易** |
| TCP | 尝试建连，端口打开即健康（立即关闭也算） | 低，无需改造 | 无 HTTP 栈的服务；只能证明"在 listen" |
| gRPC | `grpc.health.v1.Health/Check`，`status==SERVING` | 中，需实现标准 health 服务 | gRPC 服务；K8s 自 v1.27 内置 grpc probe（TLS 模式 v1.37 Alpha 默认关） |

gRPC 规范要点（官方 `doc/health-checking.md`）：客户端**必须给 Check 设 deadline**；空字符串 service 表示整体健康；`Watch` 立即回当前状态并在变化时推送。

### 6.2 超时策略参数表（K8s 官方默认 + 本地建议）

| 参数 | K8s 默认 | 本地建议 | 说明 |
|---|---|---|---|
| `initialDelaySeconds` | 0 | 3–5s + **抖动 ±20%** | 按子进程冷启动 P99；慢启动改用 startup probe 思路 |
| `periodSeconds` | 10 | 5s | 本地低延迟 |
| `timeoutSeconds` | 1 | 2s | 避免误杀慢响应 |
| `successThreshold` | 1 | 1（liveness 必须 1） | 失败后需连续几次成功 |
| `failureThreshold` | 3 | 3（≈15s 才判定） | 容忍抖动 |
| `terminationGracePeriodSeconds` | 30 | 5–10s | 优雅关闭宽限期 |
| 重启退避 | CrashLoopBackOff | `1s × 2^n`，上限 30–60s，**full jitter** | 防 thundering herd |

**关键公式**：若启动常超过 `initialDelay + failureThreshold × period`，应改用 startup probe（failureThreshold 可设高），不要放宽 liveness——否则丧失死锁检测能力。健康状态用三态（healthy / unhealthy / unknown），`unknown` 不触发动作。

### 6.3 优雅关闭与进程树杀死（三平台差异，A 级）

| 维度 | Linux | macOS | Windows |
|---|---|---|---|
| 软终止 | SIGTERM | SIGTERM | **无原生 SIGTERM**（Node：`'SIGTERM' is not supported on Windows, it can be listened on`） |
| Ctrl+C/Break | SIGINT | SIGINT | `CTRL_C_EVENT` / `CTRL_BREAK_EVENT` |
| 进程组 kill | `kill(-pid, sig)` | `killpg`，语义一致 | 无负 pid 语义；用 **Job Object** 或 `taskkill /T /F` |
| 回收 | `wait/waitpid`，否则僵尸；`PR_SET_CHILD_SUBREAPER` 接管孤儿 | 同 Unix，**无 subreaper 等价** | `WaitForSingleObject` / `CloseHandle`，无 SIGCHLD |

**Windows 关键事实**：
- `GenerateConsoleCtrlEvent`：`CTRL_C_EVENT` **不能定向进程组**（非零 pgid 时"success but not received"）；**`CTRL_BREAK_EVENT` 可定向进程组**，但发送方必须共享同一控制台，且自己也可能收到（需 `SetConsoleCtrlHandler(NULL, TRUE)` 豁免）。
- Job Object：`CreateJobObject` + `AssignProcessToJobObject`；进程加入后其 `CreateProcess` 的后代**默认自动加入**；设 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 后关最后句柄即杀光；`TerminateJobObject()` 一次性杀光。**不要设 `BREAKAWAY_OK` / `SILENT_BREAKAWAY_OK`**（否则子进程逃逸）。
- Go 运行时：`os.Interrupt` 是 Windows 上唯一可用信号；`Process.Signal(os.Interrupt)` 在 Windows 未实现（返回 error）→ 需 `golang.org/x/sys/windows` 直调 `GenerateConsoleCtrlEvent`。

### 6.4 代码骨架：跨平台进程组初始化 + 优雅关闭

```text
// 启动阶段
child = spawn(cmd, {
  detached: true,             // Unix: 新进程组/会话组长
  createNewProcessGroup: true, // Windows: CREATE_NEW_PROCESS_GROUP
  env: { ..., PORT: assignedPort }
})
if IS_WINDOWS:
  job = CreateJobObject()
  SetInformationJobObject(job, KILL_ON_JOB_CLOSE)  // 不设 BREAKAWAY_OK
  AssignProcessToJobObject(job, child.handle)      // 后代自动纳入

// 关闭阶段
func shutdown(child, graceMs):
  if IS_WINDOWS: GenerateConsoleCtrlEvent(CTRL_BREAK_EVENT, child.pid) // 软关闭
  else:          kill(-child.pid, SIGTERM)   // 负 pid = 整个进程组
  wait(child, timeout=graceMs)
  if still alive:
    if IS_WINDOWS: TerminateJobObject(job)
    else:          kill(-child.pid, SIGKILL)
  reap(child)   // Unix: waitpid；Windows: CloseHandle
```

**Go（Unix）关键实现**：

```go
cmd := exec.Command(bin, args...)
cmd.SysProcAttr = &syscall.SysProcAttr{Setpgid: true} // 关键：独立进程组
cmd.Start()
pgid := cmd.Process.Pid                              // 组长 PID == PGID

_ = syscall.Kill(-pgid, syscall.SIGTERM)             // 负号 = 整组
time.AfterFunc(grace, func() { _ = syscall.Kill(-pgid, syscall.SIGKILL) })
cmd.Wait()                                           // 回收，避免僵尸
```

> `pgid == pid` 守卫是 load-bearing 的：没设 `Setpgid` 时子进程继承父进程组，负 PGID 会**误杀自己**。若子进程自己 `setsid()` 逃逸，Linux 可用 `PR_SET_CHILD_SUBREAPER` / cgroup 兜底，macOS 无等价机制（需父进程存活期主动管理）。

### 6.5 可复用实现参考

- **MCP Python SDK `stdio.py`**（A 级，见 §10）：`start_new_session=True`（Unix 独立进程组）+ Windows Job Object；关停序列 `close stdin → 2s → terminate tree → 2s → SIGKILL → close job`，用 `CancelScope(shield=True)` 防止 LLM 取消打断清理。**这是全清单工程上最可靠的进程层参考。**
- **Kubernetes probes**：liveness（重启）/ readiness（摘流量）/ startup（慢启动）三分；Pod 终止 30s 宽限 + preStop hook → SIGTERM → SIGKILL。
- **HashiCorp Nomad**：`check{grpc/http/tcp/script}`；`kill_signal` 默认 SIGINT（Windows raw_exec 为 `CTRL_BREAK_EVENT`）、`kill_timeout` 5s、`shutdown_delay` 在摘注册与发信号之间留在途请求窗口。
- **Node**：`@godaddy/terminus`（健康检查 + 优雅关闭，README 明说 Windows SIGTERM 永远不工作）、`lightship`（独立 HTTP 暴露 probe）、`http-terminator`（排空 keep-alive，`server.close` 只停止接受新连接）。

## 7. 日志收集与聚合

### 7.1 关键结论：stdio 管道为主，不需要文件 tail

编排器自己 spawn 并持有子进程 stdout/stderr 管道时，**文件 tail 是多余且更脆弱的一层**：

| 维度 | stdio 管道（推荐主路径） | 文件 tail（fallback） |
|---|---|---|
| 实时性 | 内核 pipe，写入即达 | 轮询（默认 1s）/ inotify，有延迟 |
| rotation / inode | **不存在** | 核心痛点（`-f` 默认跟踪 fd，rename/create 后旧 inode 停读） |
| 元数据归属 | 天然知道来自哪个子进程 fd | 靠文件名/目录约定，易错 |
| 部署依赖 | 无外部命令、无文件权限、无 Windows tail 缺失问题 | 需文件可写 + rotate 协同；**Windows 无原生 tail** |
| 历史回放 | 无 | 可 |
| 风险 | **必须并发 drain 两条流**，否则管道满 → 子进程阻塞死锁 | 句柄不阻塞子进程 |

> 若必须 tail 文件：GNU `-F` = `--follow=name --retry`；BSD `-F` 仅 "keep retrying"；库推荐 Go `nxadm/tail`（hpcloud/tail 的活跃维护 fork，支持 Windows）、Node `always-tail` / `better-tail`、Rust `staart`（Windows 行为与 Linux 不完全一致，需实测）。用户提到的 `nzrm/tail` 未检索到，疑似 `nxadm/tail` 笔误。

### 7.2 结构化日志

- **JSON Lines / NDJSON**：每行一个 JSON 对象，最轻量、跨语言、可被 `jq`/SQLite 消费。OTel 提醒："JSON 编码 ≠ 自动结构化"，真正结构化要求稳定 schema。
- **OpenTelemetry Logs**：数据模型 Stable；核心字段 `Timestamp/SeverityNumber/Body/Resource/Attributes/TraceId/SpanId`。语言实现：C++/C#/Java/PHP Stable，Go/Rust Beta，JS/Python Ruby Development。Collector `filelogreceiver` 可解析任意文件。
- **库选择**：Node `pino`（零反射、sonic-boom 异步写，事实标准）；Go **标准库 `log/slog`**（Go 1.21，`JSONHandler` 行分隔 JSON、`LogAttrs` 零分配）或 `zap`/`zerolog`；Rust `tracing` + `tracing-subscriber`（结构化事件 + span，表达因果关系）。
- **多进程统一收集的价值**：每个子进程注入 `run_id/proc_id` 作为固定 attr（slog `With` / pino `child` / tracing span field），统一 `level`，落 SQLite 后按 `proc + level + 时间窗` 查询。

```json
{"timestamp":"2026-11-20T10:00:00.123Z","level":"INFO","service":"worker-2",
 "run_id":"r-42","message":"task done","duration_ms":17}
```

### 7.3 嵌入式 viewer

| 方案 | 项目 / 做法 | 许可 / 状态 | 适配 |
|---|---|---|---|
| 自建 Web | **SSE** 推流（`/logs/stream?run_id=`）+ SQLite 历史查询 | — | 依赖最少，单向足够，**推荐** |
| 单二进制 Web UI | **Logdy**（`logdyhq/logdy-core`），stdin/文件/socket/REST 多输入 + Go library 内嵌 | v0.17.0；⚠️ LICENSE 具体条款本轮未核实（D 级），商用前确认 | 最贴合"本地 Web UI + 实时推流" |
| 终端 TUI | **lnav**（`lnav/lnav`），BSD-2-Clause，多文件按时间合并 + SQLite 索引 + SQL 查询 + JSON pretty，含 Windows 二进制 | 活跃 | 调试期 `tee` 一份 JSONL 给 lnav 看 |
| 存储 | SQLite 一张 `logs(ts, run_id, stream, level, msg, attrs_json)` 表 | — | 零运维，单文件 |

**推荐组合**：stdio drain → 行帧重组（`bufio.Scanner`）→ JSONL → SQLite + SSE；开发调试时同一流 `tee` 给 lnav / Logdy。

### 7.4 代码骨架（Go）

```go
// 两条流必须并发 drain，避免 pipe 缓冲写满导致子进程卡死
for _, s := range []struct{ name string; r io.Reader }{
    {"stdout", cmd.StdoutPipe()}, {"stderr", cmd.StderrPipe()},
} {
    go func(s struct{ name string; r io.Reader }) {
        sc := bufio.NewScanner(s.r) // 行帧重组，处理跨 chunk 的半行
        for sc.Scan() {
            bus <- LogRec{RunID: runID, Stream: s.name, Line: sc.Text(), Ts: time.Now()}
        }
    }(s)
}
```

## 8. 跨平台风险清单（Windows / macOS / Linux）

### 8.1 信号与进程树（最易踩雷）

| 风险 | 平台 | 影响 | 规避 |
|---|---|---|---|
| 无 SIGTERM / SIGKILL | Windows | `kill('SIGTERM')` 是伪优雅，子进程无清理机会 | 用 CTRL_BREAK + Job Object；不赌信号语义 |
| CTRL_C_EVENT 不能定向进程组 | Windows | 发给特定子进程组无效 | 用 CTRL_BREAK_EVENT + CREATE_NEW_PROCESS_GROUP + 同控制台 |
| Go `Process.Signal` 未实现 | Windows | 标准 API 返回 error | `x/sys/windows` 直调 Win32 |
| breakaway 标志逃逸 | Windows | 子进程脱离 Job，杀不干净 | 不设 `BREAKAWAY_OK` / `SILENT_BREAKAWAY_OK` |
| 父死子留孤儿 | macOS | 无 Linux `PR_SET_CHILD_SUBREAPER` 等价 | 父进程存活期主动管理；子进程退出时自清后代 |
| PID 复用误杀 | 全平台 | `kill`/`taskkill` 按 PID，复用后误杀 | 用进程组/Job 句柄，不用裸 PID；`kill(-pgid)` 守卫 |
| 僵尸进程 | Unix | 不 `waitpid` 则 PID/FD 泄漏 | 持续 reap；Linux 可设 subreaper |

### 8.2 路径与参数转义

| 风险 | 平台 | 影响 | 规避 |
|---|---|---|---|
| `.bat`/`.cmd` 不能直接 execFile | Windows | 官方："not executable on their own without a terminal" | `spawn('cmd.exe', ['/c', 'x.bat'])`；`shell:true` 触发 DEP0190 不推荐 |
| 命令行单字符串重解析 | Windows | 含空格/引号/`%`/`^` 参数易注入/错解 | 用参数数组；`windowsVerbatimArguments:false`；绝不 splice 用户输入进 shell |
| PATH 隐式追加 `.exe/.cmd/.bat` | Windows | 解析顺序非预期 | `where`/`which` 显式解析并记录实际路径 |
| MAX_PATH=260 | Windows | 深层路径 ENAMETOOLONG | manifest `longPathAware` + 注册表 `LongPathsEnabled`；统一短根路径 |
| 大小写敏感 | Linux vs macOS/Windows | 大小写不同的模块路径在 Linux 才暴露 | 统一小写或严格按实际大小写 |
| stdio 弹控制台窗口 | Windows | GUI/服务模式弹窗 | `windowsHide: true` |

### 8.3 权限

| 风险 | 平台 | 规避 |
|---|---|---|
| 无 setuid；UAC 下无法静默提权 | Windows | 不设计"静默提权"；需高权限则用户以管理员启动编排器或装服务 |
| 公证 / Gatekeeper / TCC | macOS | 编排器以签名 .app 分发时，其拉起的子进程也受约束 → 子进程同样签名/公证；TCC 权限放同一签名 bundle；`xattr -d com.apple.quarantine` 仅开发期 |
| capabilities（CAP_KILL 等 41 项） | Linux | 最少能力运行；跨 UID 发信号需 CAP_KILL 或同 UID |

### 8.4 后台服务模式

| 平台 | 推荐机制 | 关键配置 |
|---|---|---|
| 通用 | **前台进程 + 外部托管**（首选） | 编排器保持前台、日志走 stdout；重启/daemon 化交给 OS |
| Linux | systemd unit | `Restart=on-failure`、`StartLimitIntervalSec/Burst`；user service 在 `~/.config/systemd/user/` |
| macOS | launchd plist | `KeepAlive`、`RunAtLoad`、`StandardOutPath`；关机/登出发 SIGTERM；macOS 13+ 用 `SMAppService` |
| Windows | SCM / Windows Service | `sc.exe create ... start= auto/delayed-auto`；失败恢复 `sc.exe failure ... actions= restart/60000` |

**取舍**：优先"前台 + 外部托管"——三平台只维护一套前台逻辑，日志复用 stdio 管道（§7），崩溃恢复由 OS 原生做。仅当必须自安装服务时才写三平台适配层，且需注意"作为服务无控制台"→ 信号/控制台事件语义变化、日志转向文件/事件日志。

### 8.5 端口与网络

| 风险 | 平台 | 规避 |
|---|---|---|
| 保留端口（Hyper-V/WSL2/Docker） | Windows | bind(0) + fd 传递；`netsh show excludedportrange` 诊断 |
| ephemeral 段不同 | 全平台 | 不硬编码端口段；让内核分配 |
| SCM_RIGHTS / WSADuplicateSocket 语义差异 | Unix vs Windows | 平台抽象层内实现，业务代码只见"传 fd"接口 |

- **只借鉴、不 fork 的**：MCP **Python SDK `stdio.py`**（进程生命周期协议，工程最可靠）；MCP TS SDK（env 白名单、stderr PassThrough）；`mcp-sidecar`（极简 6 工具接口、`maxBytes` 上限、白名单/审计）；`mcpmu`（namespace/权限模型、工具 schema 压缩降 LLM context 成本）；`dumb-init`/`tini`（容器 PID1 场景）。
- **明确不 fork**：pm2（AGPL + 无 ready 探针）、mcp-manager（FSL 生产受限）、E2B（层不同）、Cline/Continue（进程层不可独立抽出）、foreman/honcho/overmind（停滞、无健康检查）。
- **为什么通用 PM 不直接适用 AI agent 场景**（6 条）：① 短命 vs 长驻语义冲突（MCP stdio server 无输入即退出，通用 PM 会无限拉起 → "infinite crash loop"）；② 动态端口需运行时分配并回填；③ 需要结构化事件流而非文本日志；④ 生命周期与工具调用绑定（取消必须清理且不被取消打断）；⑤ 需要可执行白名单/审计/工具 allow-deny；⑥ 需跨平台进程树杀死。

## 10. 推荐技术栈（整合）

### 10.1 主推方案：Go 薄编排内核 + MCP stdio 生命周期协议

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 / 运行时 | **Go**（单静态二进制） | 交叉编译最简单、os/exec 够用、体积最小 |
| 进程启动 | `os/exec` + `SysProcAttr{Setpgid}`（Unix）/ Job Object（Windows） | 标准库覆盖 spawn/stdio/context 取消 |
| 进程生命周期协议 | **借鉴 MCP Python SDK `stdio.py`** | 有界等待 + shield 关停序列是全清单最可靠参考 |
| 动态端口 | `bind(0)` + `getsockname` + `SCM_RIGHTS` / `WSADuplicateSocket`；env `PORT` 兜底 | 零 TOCTOU |
| 健康检查 | HTTP `/healthz`（HTTP 优先）/ TCP / `grpc.health.v1`；K8s 参数 + 抖动 | 易调试、可携带依赖状态 |
| 优雅关闭 | `SIGTERM/CTRL_BREAK → grace → SIGKILL/TerminateJobObject` + reap | 跨平台统一策略 |
| 日志 | stdio 管道并发 drain → `bufio.Scanner` 行帧 → `log/slog` JSONL → SQLite + SSE | 无 rotation 痛点、无外部依赖 |
| 结构化 | 固定 `run_id` attr + 统一 `level` schema | 可查询、与 LLM 事件流对齐 |
| viewer | SSE 自建 Web + SQLite；调试期 `tee` 给 lnav/Logdy | 依赖最少 |
| 服务模式 | 前台进程 + systemd / launchd / SCM | 三平台一套逻辑 |

### 10.2 备选方案：Node + execa（上游 worker 全是 Node/TS 时）

- 用 `execa` 的 `killDescendants` + `forceKillAfterDelay` 直接解决树形杀死与兜底强杀；
- 动态端口仍用 bind(0)，Node 层用 `child_process` 的 `stdio: [fd]` 传递已 bind 的监听 fd（Windows 用 `windowsVerbatimArguments:false`）；
- 日志用 `pino` + child logger；健康检查用 `lightship` + `http-terminator`；
- 代价：runtime 开销、SEA 分发限制、守护语义需自补；`@godaddy/terminus` 明确 Windows 信号残缺。

## 11. MVP 实现路线图

| 阶段 | 目标 | 关键交付 | 验收标准 |
|---|---|---|---|
| **P0 · 进程生命周期内核**（1–2 周） | 先解决"唯一真正要造的轮子" | 三平台进程抽象：`spawn` + 独立进程组/Job Object + `shutdown(grace)` + 强制升级 + reap；端口模块 `bind(0)` + fd 传递 + env 兜底 | 三平台各起一个"会 fork 孙进程"的测试子进程；发关停后孙进程零残留、无僵尸；连续 100 次 spawn/teardown 无 fd/PID 泄漏 |
| **P1 · 健康检查 + 重启策略**（1 周） | 从"能启动"到"知道是否可用" | HTTP/TCP probe、三态状态机、K8s 参数表 + 抖动、CrashLoopBackOff 退避、事件流输出 | 注入"启动慢 / 假死 / 抖动"故障，能正确区分 startup/readiness/liveness；重启加抖动后无同步风暴 |
| **P2 · 日志聚合 + viewer**（1 周） | 让多进程日志可用 | stdio 并发 drain → 行帧 → JSONL → SQLite 表；SSE 推流 viewer；run_id 注入 | 单进程写 10 万行不阻塞；跨 chunk 半行正确重组；按 run_id + level + 时间窗可查 |
| **P3 · 三平台硬化**（1 周） | 把差异点变清单驱动测试 | Windows：保留端口诊断、长路径 manifest、`.bat` 启动、CTRL_BREAK；macOS：公证/TCC 文档；Linux：capabilities 最小化；CI 三平台矩阵 | §8 风险清单逐条有对应测试用例或明确豁免说明 |
| **P4 · AI 控制面（可选）**（1–2 周） | 与 LLM 工具调用生命周期绑定 | 借鉴 `mcp-sidecar` 6 工具接口 + 白名单/审计；`CancelScope(shield)` 等价的"取消不打断清理"；并发上限 + 输出上限 | 一次工具调用 = spawn→ready→call→teardown；调用取消后进程与端口确定性回收 |
| **P5 · fork 评估门**（决策点） | 判断是否切换到 process-compose | 若 P0–P4 自研成本 > fork + 改造成本，则切 `process-compose` 并移植动态端口/事件流 | 用同一组端到端用例对比自研与 fork 分支，取通过率与代码行数比 |

**关键顺序理由**：P0 先做进程生命周期，因为它是唯一无法回避的自研工作，也是所有上层能力的地基；端口与生命周期强耦合（fd 传递），必须同阶段完成。P3 不能拖到最后——三平台差异会反向影响 P0/P1 的接口设计，建议在 P0 就建立三平台 CI 骨架。

## 13. 存疑与待核实清单（D 级）

1. **性能/体积数字**：除 `yq-core` 自报基准外均为经验量级，无官方三语言基准；目标硬件上需自测。
2. **Rust musl 静态**：官方 target 页本轮 404，未核实；若改选 Rust 需补。
3. **macOS / Windows TIME_WAIT 精确值**：macOS ~30s、Windows `TcpTimedWaitDelay` 默认 240s 均为第三方说法，非官方一手。
4. **许可证细节**：pm2（AGPL vs README 表述差异）、supervisor / s6-overlay（GitHub `NOASSERTION`）、Logdy LICENSE 条款——商用/分发前逐字核对仓库 LICENSE 文件。
5. **process-compose 树形杀死与原生动态端口**：仅确认支持 fork/daemon 与 `pc_process_ports` 回报，未逐字核实源码；fork 前需读源码确认。
6. **mcp-sidecar 是否进程树级杀死**：README 仅称"server 退出时终止所有子进程"，未确认树级。
7. **Rust 健康检查库 API 名**（`axum::with_graceful_shutdown` 等）未一手核实。
8. **"Michael+X"**：原始需求提到该名称，未能定位具体项目，疑为笔误/小众项目，需确认。
9. **Node Windows 信号 v18 vs v24 措辞差异**：行为结论一致（强制终止），目标 Node 版本实测。
10. **macOS Gatekeeper "未签名代码默认不运行"**：来自 WWDC19 表述，具体生效版本与例外未逐条确认。
