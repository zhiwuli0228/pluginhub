## 0. 结论先行

### 0.1 一句话判断

**没有"一个协议通吃"的选项，但存在一个稳定的三层分工：`发现层`（AI Catalog）→ `打包层`（Agent Plugins / Skills）→ `调用层`（MCP 管工具、A2A 管 Agent）。管理器不应该押注单一协议，而应该把这三层各自的事实标准都收进来，再用自己的统一能力模型做归一。**

### 0.2 选型结论表

| 协议 / 标准 | 在管理器中的角色 | 结论 | 核心理由 | 主要风险 |
|---|---|---|---|---|
| **MCP**（2026-07-28） | 工具 / 资源接入的**主通道** | **原生支持（Tier 0）** | 供给端碾压：官方注册表 6.3–6.5 万 server，SDK 月下载约 6.5 亿，GitHub `mcp-server` 主题 4.3 万仓库 | 2026-07-28 去掉会话与 `initialize`，历史 server 兼容成本高；生态安全欠账多 |
| **Agent Skills**（SKILL.md） | 程序性知识的**打包单元** | **原生支持（Tier 0）** | 70+ 平台采纳，渐进式加载（~100 token/技能）天然适配上下文预算 | 规范无版本号、无 registry、无权限模型，`allowed-tools` 仅实验性 |
| **Agent Plugins 1.0** | 外部插件的**导入格式** | **原生支持为"导入器"，不作为自家清单** | 事实上的跨客户端打包标准（Amazon / Cursor / Microsoft / OpenAI / Vercel / Google） | 无信任模型、无权限、无密钥机制；与 Claude Code 的 `plugin.json` 同名冲突；Anthropic 缺席 |
| **A2A**（1.0.1 / 1.1-rc） | 跨组织 Agent 委派的**唯一可行通道** | **原生支持（Tier 1）** | Linux Foundation / AAIF 治理，Google Cloud、Bedrock AgentCore、Azure AI Foundry 原生支持 | 实际部署仍以 0.3 为主；卡片签名默认 HS256 有伪造风险；与 MCP 边界正在模糊 |
| **AI Catalog / ARD** | 域名级**统一发现入口** | **原生支持（Tier 1，探测式）** | 一个 `/.well-known/ai-catalog.json` 同时索引 MCP / A2A / API，带 trust manifest 与三级一致性 | 仍是草案；字段名在 WG 内仍在变；实测渗透率极低 |
| **OpenAPI 3.x** | 存量 REST 的**适配层** | **适配器支持（Tier 2）** | 存量资产最大，零改造成本；A2A 的 auth scheme 直接复用 | 静态描述、无流式、无会话；全量导入会撑爆上下文 |
| **Arazzo 1.0 / agents.json** | 多步流程的**确定性编排** | **适配器支持（Tier 2）** | 把多步调用压成单个工具，显著降低 LLM 编排错误 | agents.json 已停更（2025-08 后无提交），实质是孤儿标准 |
| **AGNTCY（OASF / DIR / SLIM / ACP）** | 联邦注册表与**能力分类法** | **仅导入 / 同步（Tier 2）** | OASF 的 skill/domain 层级分类是全行业最完整的能力词表 | DIR 仓库 205 stars，采用率低；SLIM/ACP 与 A2A 功能重叠 |
| **ANP / NANDA** | 去中心化身份与检索 | **观察，不投入（Tier 3）** | DID 身份模型在跨信任域场景理论上最优 | 无生产实现，工具链滞后，元协议协商增加延迟 |
| **MCP Apps**（SEP-1865） | 富交互 UI | **按宿主能力渲染（Tier 2）** | 已是 MCP 首个官方扩展，ChatGPT / Claude / VS Code 已支持 | 需沙箱 iframe + CSP，安全评审面扩大 |

### 0.3 三条反直觉结论

1. **"发布 well-known 文件" ≠ "会被发现"。** 2026-10 对 10,809 个自有域名服务的探测中，629 个提供 A2A agent card，573 个有 `llms.txt`，只有 **186 个**提供 MCP server card；而 `llms.txt` 有 97% 的文件在 2026-05 整月零请求 `【实测】`。管理器不能只靠 well-known 探测，必须 registry + 探测 + 本地扫描三路并行。
2. **统一清单的真实瓶颈不是字段，是"权限 + 信任 + 密钥"。** Agent Plugins 1.0 只定义了两个必填字段（`$schema`、`name`），却因为不定义权限模型，使"安装插件 = 执行代码"。这恰好是管理器最该补的一层。
3. **协议越多，兼容层成本呈超线性增长。** 从 OpenAPI → RPC → MCP → A2A → Agent Plugins，每一层都解决上一层的问题、又引入新的抽象。管理器的护城河不是"支持最多协议"，而是"用最少的归一化损失支持最关键的子集"。

## 2. 协议逐个解剖

### 2.1 MCP（Model Context Protocol）

#### 2.1.1 版本与治理

| 项 | 内容 |
|---|---|
| 当前规范 | **2026-07-28**（前一版 2025-11-25，再前一版 2025-06-18）`【规范】` |
| 治理 | 2025-12 捐赠给 Linux Foundation 下的 **Agentic AI Foundation（AAIF）**；AAIF 成员组织 286 家（2026-10）`【官方】` |
| 传输 | `stdio`、`Streamable HTTP`（`HTTP+SSE` 自 2025-03-26 起弃用，2026-07-28 正式归类为 Deprecated）`【规范】` |
| 授权 | OAuth 2.1 + RFC 9728 Protected Resource Metadata；2026-07-28 把 DCR（RFC 7591）降级，改用 **Client ID Metadata Documents** `【规范】` |

#### 2.1.2 元数据结构（这是清单设计要映射的核心）

**服务端三原语**

| 原语 | 控制方 | 关键字段 | 与清单的关系 |
|---|---|---|---|
| `Tool` | 模型控制 | `name`、`title`、`description`、`inputSchema`（JSON Schema 2020-12）、`outputSchema`、`annotations`、`_meta` | 清单的 `routing.intents[].capabilityRefs` 要引用到 tool 级 |
| `Resource` | 应用控制 | `uri`、`name`、`mimeType`、`size`、`annotations` | 可作为技能的 `references/` 替代通道 |
| `Prompt` | 用户控制 | `name`、`title`、`arguments`、`icons` | 语义上最接近"技能"，但只承载模板，不承载脚本 |

**工具注解（跨协议唯一的通用副作用语义，务必进统一模型）**`【规范】`

| 注解 | 含义 | 调度价值 |
|---|---|---|
| `readOnlyHint` | 无副作用 | 可并发、可缓存、可免审批 |
| `destructiveHint` | 会删除 / 覆盖 | **必须**走审批门 |
| `idempotentHint` | 同参重试安全 | 决定重试策略 |
| `openWorldHint` | 结果集开放（外部 API） | 决定是否需要结果裁剪与超时保护 |

**2026-07-28 的关键变更（直接影响适配层实现）**`【规范】`

| 变更 | SEP | 对管理器的含义 |
|---|---|---|
| 删除协议级会话与 `Mcp-Session-Id` | 2567 | 不能再靠 session 粘性路由；负载均衡可无状态，但**服务端需要显式句柄**（如 `task_id`）作为普通参数传递 |
| 删除 `initialize` 握手，改全无状态 | 2575 | 每个请求在 `_meta` 里带 `protocolVersion` / `clientCapabilities`；管理器必须在每次调用注入，而不是启动时协商一次 |
| 新增 `server/discover` | 2575 | **这是最靠谱的运行时自描述入口**：返回支持的协议版本、能力与身份。适配层应优先调它而不是 probe 猜测 |
| `subscriptions/listen` 取代 GET 端点与 `resources/subscribe` | 2575 | 一条长连接 POST 流承载变更通知，客户端按类型 opt-in |
| 任务移出核心，成为扩展 `io.modelcontextprotocol/tasks` | 2663 | 长任务要靠扩展协商，不能假设核心有 task |
| MRTR（多轮往返请求）取代服务端反向请求 | 2322 | `sampling` / `elicitation` / `roots` 改为"返回 `input_required` + 客户端重试"。**这是最容易把老适配器写错的地方** |
| 结果必带 `resultType` | 2322 | 老 server 缺该字段时按 `complete` 处理 |
| `extensions` 字段进入双方 capabilities | — | 扩展协商有了正式位置（MCP Apps 走这里） |
| 列表结果必带 `ttlMs` / `cacheScope` | 2549 | **缓存有官方语义了**：管理器可按 `ttlMs` 做工具清单缓存，`cacheScope` 决定能否共享缓存 |
| `tools/list` 应确定性排序 | — | 提升 prompt cache 命中率；管理器不应打乱顺序 |
| 弃用 Roots / Sampling / Logging | 2577 | 12 个月弃用窗口；新建适配器不要再依赖这三个 |

#### 2.1.3 发现路径（三条，优先级不同）

| 路径 | 位置 | 成熟度 | 内容边界 |
|---|---|---|---|
| 官方 Registry | `registry.modelcontextprotocol.io` `/v0/servers` | 预览→规模最大 | 反向 DNS 命名空间 + `server.json`（`packages` / `remotes`） |
| Server Card | SEP-2127（WG 草案，取代 SEP-1649） | **实验性** | **故意不含 tools / resources / prompts**：因为原语随用户身份、配置、feature flag 变化，静态文档无法可靠表达 |
| 运行时自描述 | `server/discover` | 2026-07-28 起 MUST | 协议版本、能力、身份 |

> **设计启示**：Server Card 明确"不承诺原语清单"，所以管理器**不能**只靠卡片建索引，必须在连接后调 `tools/list` 做二次索引，并用 `ttlMs` 控制刷新。

#### 2.1.4 扩展：MCP Apps（SEP-1865）

- 官方首个扩展，ext id `io.modelcontextprotocol/ui`，稳定版 2026-01-26 `【规范】`
- 机制：工具在 `_meta.ui.resourceUri` 指向 `ui://` 资源（`text/html;profile=mcp-app`），宿主在**沙箱 iframe** 渲染，通过 `postMessage` 上的 JSON-RPC 方言通信
- 安全：CSP 默认 `default-src 'none'`，外域必须显式声明 `connectDomains` / `resourceDomains` / `frameDomains`；能力（摄像头、地理位置等）需 `_meta.ui.permissions` 申请
- **对管理器**：这是"插件 UI"的既成事实标准，自研 UI 协议没有意义；但渲染前必须做模板预审（因为模板可代表用户发起工具调用）

### 2.2 A2A（Agent-to-Agent）

#### 2.2.1 版本与治理

| 项 | 内容 |
|---|---|
| 稳定版 | **1.0.1**（2026-05-28）`【官方】` |
| 候选版 | **1.1.0-rc**（dev-1.1 线，2026-10-29 打 tag，无 GitHub Release）`【实测】` |
| 治理 | Google 2025-04 发起 → 2025-06 捐 Linux Foundation → **2026-08-17 以 Growth Stage 进入 AAIF**（与 MCP 同基金会）`【官方】` |
| 规范形态 | `a2a.proto` 为规范性来源，JSON / SDK 绑定由其生成；JSON Schema 2020-12 发布 `【规范】` |
| 绑定 | JSON-RPC 2.0、gRPC、HTTP+JSON（v1.0 的 `supportedInterfaces` 有序列表）`【规范】` |

#### 2.2.2 Agent Card 字段（清单要映射的对象）

```json
{
  "name": "Example Agent",
  "description": "An example agent that echoes messages.",
  "supportedInterfaces": [
    { "url": "https://example.com/a2a/v1", "protocolBinding": "JSONRPC", "protocolVersion": "1.0" }
  ],
  "version": "1.0.0",
  "capabilities": { "streaming": false, "pushNotifications": false, "extensions": [] },
  "defaultInputModes": ["text/plain"],
  "defaultOutputModes": ["text/plain"],
  "skills": [
    { "id": "echo", "name": "Echo", "description": "Echoes the input.", "tags": ["echo"] }
  ]
}
```

| 字段组 | 字段 | 说明 |
|---|---|---|
| 必填（8 项） | `name` `description` `version` `supportedInterfaces` `capabilities` `defaultInputModes` `defaultOutputModes` `skills` | v1.0 起 `url` 被 `supportedInterfaces` 有序列表取代 |
| 接口选择 | `protocolBinding` ∈ {JSONRPC, GRPC, HTTP+JSON}；`protocolVersion` 用 Major.Minor | 客户端 MUST 选第一个自己支持的条目；`tenant` 必须与选中条目一致 `【规范】` |
| 能力 | `streaming`、`pushNotifications`、`extendedAgentCard`、`extensions` | 声称 `streaming=true` 才能用流式操作 |
| 技能 | `id` `name` `description` `tags` + 可选 `examples` `inputModes` `outputModes` `securityRequirements` | **技能是"能力声明"，不是函数签名**——没有 JSON Schema 式参数契约 |
| 可选 | `provider` `documentationUrl` `iconUrl` `securitySchemes` `securityRequirements` `signatures` | `signatures` 为 JWS，可多签名 |

**核心对象模型**

| 对象 | 语义 | 关键点 |
|---|---|---|
| `Task` | 有状态工作单元 | 9 态：`SUBMITTED` `WORKING` `INPUT_REQUIRED` `AUTH_REQUIRED` `COMPLETED` `FAILED` `CANCELED` `REJECTED` `UNSPECIFIED` |
| `Message` | 一轮对话 | 含多个 `Part`：text / raw bytes / URL / structured data |
| `Artifact` | 交付物 | **不进 Message**，有独立 ID，隐含版本 |
| `Extension` | 能力扩展 | x402 支付等走这里 |

**1.1-rc 的四个变化（决定是否提前适配）**`【实测】`

| 变化 | 含义 |
|---|---|
| `Task.generation` 单调递增 | 支持长轮询（`current_generation`）与乐观并发（`if_generation_match`，失败返回 HTTP 412 / gRPC ABORTED）——**多个客户端安全共管一个远程任务是刚需** |
| `SendLiveMessage` | 双向交互，从"发任务-等结果"变成"可中途对话" |
| 客户端可写 Artifact | 结果不再单向 |
| 发现顺序调整 | **优先 AI Catalog，其次 well-known URI**；新增媒体类型 `application/a2a-agent-card+json` |

#### 2.2.3 安全：卡片签名有一个真实的坑

`【社区/实测】` `a2a-sdk` 的卡片签名**默认 HS256（对称）**。对公开分发的 Agent Card 而言，验签密钥 = 伪造密钥，等于没有签名。正确做法：

1. 用 **EdDSA / ES256** 等非对称算法签名；
2. 验签时传**显式算法白名单**（否则触发经典 JWS `alg` 混淆攻击）；
3. 无 `signatures` 的卡片是**自证**（self-asserted），有效签名只证明"某把密钥签的"，**不证明这把密钥可信**——密钥必须带外 pin 或来自已信任的 JWKS。

> **对管理器**：`trust` 字段必须区分 `signed` / `verified` / `trusted` 三态。把"验签通过"直接当"可信"是供应链攻击的入口。

### 2.3 Agent Skills 与 Agent Plugins（打包层）

#### 2.3.1 Agent Skills

| 项 | 内容 |
|---|---|
| 形态 | 一个目录 + 必填 `SKILL.md`（YAML frontmatter + Markdown 正文）`【规范】` |
| 必填字段 | `name`（1–64，小写字母/数字/连字符，须与父目录同名）、`description`（1–1024） |
| 可选字段 | `license`、`compatibility`（1–500）、`metadata`（string→string）、`allowed-tools`（**实验性**，空格分隔） |
| 加载机制 | **渐进式披露**：启动只载入 name + description（约 100 token/技能）→ 命中任务才读全文 → 需要时才读 `scripts/` `references/` `assets/` |
| 治理 | 2025-12 开放；**2026-10-22 捐赠给 AAIF**（含名称、logo、GitHub 组织、域名）；70+ 平台采纳 `【官方】` |

**必须知道的边界**：Agent Skills 只定义"目录内容格式"，**不定义**安装、发现位置、激活 UI、授权、沙箱、registry、版本协商。`allowed-tools` 是实验字段，各宿主解释不一。规范**没有**必填的版本字段——`metadata.version` 只是元数据，不是协议版本协商。

#### 2.3.2 Agent Plugins 1.0（最接近用户设想的"统一清单"）

| 项 | 内容 |
|---|---|
| 发布 | 2026-08 公开发布 / GA；TSC：**Amazon、Cursor、Microsoft、OpenAI、Vercel、Google**；**Anthropic 不在 TSC** `【官方/社区】` |
| 治理 | 独立治理的开源规范，**不是 AAIF 项目**，也未提交提案 |
| 结构 | `plugin.json`（根，必填）+ `skills/`（每个直接子目录含 `SKILL.md`）+ `mcp.json`（根，可选）+ 反向域名目录（如 `com.github.copilot/`） |
| 清单字段 | 必填 2：`$schema`（固定字面量）、`name`；可选 8：`version` `description` `author` `homepage` `repository` `license` `keywords` `extensions`；`additionalProperties: false` |
| 路径变量 | `${PLUGIN_ROOT}`（包内文件）、`${PLUGIN_DATA}`（跨版本持久可写） |
| 失败隔离 | 坏 `plugin.json` → 整包拒绝；坏 `SKILL.md` → 只跳过该技能；坏 MCP 条目 → 只禁用该 server |
| 生态量 | 某第三方验证目录收录 5,806 个插件（2026-11-13）：79% 带技能、34% 带 MCP、23% 两者都有 `【实测】` |

**七个已知缺陷（直接决定我们不能照抄它当自家清单）**

| 缺陷 | 细节 | 我们的对策 |
|---|---|---|
| schema 与正文自相矛盾 | schema 是 `additionalProperties: false`，正文却要求"客户端上报未知顶层字段并继续加载" | 顶层 closed + `extensions` 显式 open，并在规范里写死"未知字段忽略" |
| `plugin.json` 同名冲突 | Claude Code 用 `.claude-plugin/plugin.json`，字段集不同（含 `commands` `agents` `hooks` `mcpServers` `lspServers` `outputConfig` `userConfig`） | 用**不同文件名 + `apiVersion` 判别**，不做同名多义 |
| 无信任模型 | 安装 = 执行代码，无沙箱、无 provenance、无审批流 | `trust` + `permissions` 必填段 |
| 无密钥机制 | 不得内嵌凭证，只能依赖各客户端自己的认证流 → 实质锁死客户端 | 只允许**引用** secret（`refs`），由管理器 broker 注入 |
| 客户端扩展静默丢弃 | VS Code 明确忽略其他客户端的命名空间目录，不报错 | 加载时**显式报告被忽略的扩展**，不允许静默 |
| SSE 不兼容 | ChatGPT / Codex 只支持 stdio + Streamable HTTP | 适配层做 SSE→Streamable HTTP 桥接并告警 |
| Anthropic 缺席 | Claude Code 需另一套路径，所谓"write once"不成立 | 保留 Claude 格式导入器 |

**v1.1 路线图（可作为我们字段设计的参照）**`【社区】`：权限模型、加密签名校验、attestation 链、密钥机制、一致性测试套件、机器可读能力画像。

### 2.4 AGNTCY / BeeAI

#### 2.4.1 组件栈

| 组件 | 作用 | 关键实现细节 |
|---|---|---|
| **OASF**（Open Agentic Schema Framework） | Agent 记录 schema：skills / domains / modules 的**层级分类法** | Apache-2.0；schema server `schema.oasf.outshift.com`；版本 0.7/0.8/1.0 并存 `【官方】` |
| **Agent Directory（DIR）** | 联邦发现：发布、交换、检索 OASF 记录 | gRPC API + Go/Python/JS SDK + `dirctl`；**内容寻址（CID）+ DHT**；记录可签名；Go 仓库 205 stars（2026-11）`【实测】` |
| **SLIM** | 安全低延迟消息 | 基于 gRPC/HTTP2，**MLS（RFC 9420）端到端加密**，四级命名（org/namespace/service/client-hash） |
| **ACP**（Agent Connect Protocol） | REST 调用远程 Agent | **OpenAPI 3.1.1 定义**；数据模型 Agents / Threads / Runs / Checkpoints |
| **Identity** | 身份与信任 | W3C DID + Verifiable Credential；`/.well-known/jwks.json` 域名验证；MCP server / tool 也可发 badge |

#### 2.4.2 信任与验证机制（这是 AGNTCY 最值得抄的部分）

| 机制 | 做法 | 可复用性 |
|---|---|---|
| 域名绑定命名 | 记录名用 URL（`https://example.com/my-agent`），验签密钥从该域 `/.well-known/jwks.json` 取 | **高**，比反向 DNS 命名空间更强，因为它把"名字"和"能签名的域"绑死 |
| 内容寻址 | CID 即记录哈希，拉取后可自校验 | **高**，天然防篡改 |
| 记录签名 | 服务端验签 + 客户端可复验 | 高 |
| 可验证凭证 | badge 形式给 agent / MCP server / tool 发 VC | 中（依赖 DID 生态成熟度） |

#### 2.4.3 BeeAI 与 ACP 的归宿

BeeAI 是 IBM 系 Agent 框架，`A2AServer` / `A2AAgent` 适配器可把 BeeAI agent 变成 A2A 兼容。IBM 2025-03 提出的 REST 版 ACP 已于 **2025-08 并入 A2A**（Linux Foundation 下）`【社区】`。因此 **ACP 不应作为独立目标协议**，只作为 A2A 的一种绑定/参考实现看待。

### 2.5 OpenAPI / AsyncAPI / Arazzo：适配层的可行性与局限

#### 2.5.1 版本现状

| 规范 | 版本 | 时间 | 对 Agent 的相关性 |
|---|---|---|---|
| OpenAPI | 3.1 | 2021-02 | JSON Schema 2020-12 对齐 |
| OpenAPI | **3.2** | 2025-09 | 结构化 tag 导航、流式媒体类型、更多 OAuth 流 |
| OpenAPI | Moonwalk（下一大版） | **无计划日期** | 官方明确"今天请用 3.x"`【官方】` |
| Arazzo | 1.0 / 1.0.1 | 2024 / 2025-01 | 确定性 API 调用序列；官方 `arazzo-cli` 自带 MCP server，可把工作流当单个 tool 调用 |
| AsyncAPI | 3.1 | — | 消息/事件契约；与 OpenAPI 通过"任务 ID + 相关性"衔接 |

#### 2.5.2 四个硬局限（决定它只能做适配层，不能做原生层）

| 局限 | 具体表现 | 量化/证据 |
|---|---|---|
| **静态 vs 动态** | OpenAPI 是写死的文档；Agent 需要在运行时发现"此刻能用什么" | 无运行时能力协商，只能重启重载 |
| **人类优先 vs 机器优先** | `description` 常是一句话，LLM 需要"何时用 / 何时不用 / 前置条件" | 描述模糊 → 路由失败；缺 `operationId` → 工具名由 path+method 生成，**不稳定** |
| **上下文成本** | 全量 spec 直接塞进 prompt | 一份中等 spec 可吃掉 1/3 上下文；个别宿主有硬上限（如约 40 个工具、工具名 60 字符） |
| **HTTP 绑定** | 无 stdio、无流式语义、无长任务状态机 | 长任务只能"202 + 轮询"，语义弱于 MCP tasks / A2A Task |
| **模型侧 schema 子集** | 部分运行时支持 `anyOf` 但不支持 `allOf`/`oneOf` | 复杂 spec 需降维改写 |

#### 2.5.3 但它仍是不可或缺的一层

- **存量最大**：企业 API 几乎都有 OpenAPI，零改造成本；
- **A2A 直接复用其 auth scheme**（`securitySchemes` 同构）；
- **MCP server 常由 OpenAPI 生成**（Speakeasy / Stainless 等），是上游事实来源；
- **正确的接法是"三个元工具"而非全量暴露**：`list_endpoints` / `get_schema(operationId)` / `invoke(operationId, args)`，让 Agent 按需拉取而非预付上下文。

> **结论**：OpenAPI 是"描述层的地基"，不是"调用层的协议"。管理器应把它编译成 MCP 风格工具或 A2A 技能，而不是把它当成第三种原生协议。

## 4. 协议间的映射关系

### 4.1 概念映射总表

| 统一概念 | MCP | A2A | Agent Skills | OpenAPI / Arazzo | OASF | 归一化难度 |
|---|---|---|---|---|---|---|
| **Tool（可执行、有副作用）** | `Tool` + `inputSchema` | —（技能无参数契约） | 指令中提及的 `allowed-tools` | `operation`（`operationId`） | `module`? | 中：A2A 无 schema，需靠示例推断 |
| **Instruction / Skill（程序性知识）** | `Prompt`（仅模板） | `AgentSkill`（能力声明） | `SKILL.md`（含脚本） | — | `skill`（分类法 ID） | **高**：四者语义不同层，强行对齐会丢信息 |
| **Agent（自治主体）** | MCP Server（若带自主循环） | `AgentCard` | —（宿主即 Agent） | — | agent record | 低 |
| **Workflow（确定性多步）** | tasks 扩展 | `Task`（非确定性） | 指令内步骤 | **Arazzo** / agents.json `flows` | — | 中 |
| **Resource（只读上下文）** | `Resource`（URI） | `Artifact`（产物） | `references/` | response schema | — | 中：Artifact 是输出，Resource 是输入 |
| **副作用语义** | `annotations`（4 个 hint） | 无 | 无 | `x-` 扩展（非标准） | 无 | 低（只有 MCP 有） |
| **流式** | Streamable HTTP + `subscriptions/listen` | `capabilities.streaming` + SSE | 无 | OpenAPI 3.2 流式媒体类型 | 无 | 中 |
| **长任务** | `io.modelcontextprotocol/tasks` 扩展 | `Task` 9 态 | 无 | 202 + 轮询 | — | 中 |
| **身份** | registry 命名空间 | 域名 + JWS | 无 | OAuth `securitySchemes` | DID + VC + JWKS | 高 |
| **版本** | 日期版（2026-07-28） | Major.Minor（1.0） | **无版本号** | 3.2.x | schema 版本 | 高：Skills 无版本是硬伤 |

### 4.2 关键结论：映射不是同构的

```
MCP Tool        ──≈──  OpenAPI Operation        （都有参数契约，可机械转换）
MCP Tool        ──✗──  A2A Skill               （A2A 技能没有 schema，只有描述+标签+示例）
A2A Skill       ──≈──  Agent Skills 的 name+description   （都只是"能力声明"）
A2A Task        ──≈──  MCP tasks 扩展            （都有状态机，但 A2A 更丰富：9 态 + 人工介入）
Arazzo Workflow ──≈──  agents.json flow         （都是确定性编排，都可编译成一个 tool）
OASF skill      ──≈──  分类法 ID                 （是"标签体系"，不是"能力实现"）
```

**三个必须承认的语义落差**

1. **A2A Skill 没有参数契约**。它只有 `id/name/description/tags/examples/inputModes/outputModes`。管理器把 A2A 技能当工具调用时，**参数必须由 LLM 从描述 + 示例推断**，错误率显著高于 MCP。对策：A2A 调用一律走"委派"语义（发消息、等 artifact），不做"函数调用"模拟。
2. **Agent Skills 无版本**。规范没有必填版本字段，`metadata.version` 只是自由元数据。所以**不能靠 SKILL.md 自身做版本协商**，必须由外层清单（我们的 manifest）承担版本与兼容性声明。
3. **`prompt` ≠ `skill`**。MCP Prompt 是"参数化模板"，无脚本、无资源目录；Agent Skill 是"带脚本和参考资料的目录"。把 Prompt 映射成 Skill 会丢掉可执行能力，反之会把技能塞进 prompt 撑爆上下文。

### 4.3 双向适配的"单向门"

| 方向 | 可否自动 | 说明 |
|---|---|---|
| MCP → OpenAPI | 可（半自动） | `inputSchema` 直接转 requestBody；但 lossy：丢失 `annotations`、流式、tasks |
| OpenAPI → MCP | 可（生成器成熟） | 需人工加"何时调用"的描述与安全注解；建议只生成白名单操作 |
| MCP → A2A | **不可** | 工具不是主体，没有任务生命周期、没有 artifact |
| A2A → MCP | **不可** | Agent 是有状态主体，包成 tool 会丢 `INPUT_REQUIRED` 等人工介入点 |
| Skill → MCP Prompt | 部分 | 正文可转模板，但脚本与资源目录无处安放 |
| Arazzo → MCP Tool | 可 | 官方 `arazzo-cli` 已提供 MCP server，把工作流当单 tool |
| OASF → 任意 | 仅标签 | 只能贡献"能力分类"与检索关键词 |

### 5.2 七个真实争议点

**① schema 与正文自相矛盾（Agent Plugins）**
`additionalProperties: false` 与"客户端应忽略未知字段并继续加载"直接冲突。后果：作者无法判断加一个厂商字段会不会让整包失效。**这是可移植性最脆弱的裂缝。**

**② 同名 `plugin.json` 的语义分裂**
Agent Plugins 用根 `plugin.json`；Claude Code 用 `.claude-plugin/plugin.json`，且字段集完全不同（`commands` / `agents` / `hooks` / `mcpServers` / `lspServers` / `outputStyle` / `userConfig`）。文件名相同、语义不同，工具链与人类都会误判。

**③ 安装即执行：没有权限模型**
1.0 明确把安装、权限、沙箱、审批交给客户端，等于"标准不管安全"。`【社区】`批评："Treat every third-party plugin install as a code review, not a settings change."

**④ 没有可移植的密钥机制**
禁止内嵌凭证 → 只能依赖各客户端自己的认证流 → **反而锁死客户端**。这是"开放标准产生厂商锁定"的典型案例。

**⑤ Anthropic 缺席 = "write once" 不成立**
Agent Skills 是 Anthropic 捐的，Agent Plugins 却把它排除在 TSC 外。Claude Code 路径不兼容，目标含 Claude 的插件作者仍要维护两套。

**⑥ MCP 2026-07-28 的"无状态化"引发反弹**
删会话、删 `initialize`、删 SSE 重放、弃用 Roots/Sampling/Logging —— 换来水平扩展与边缘部署友好，代价是：
- 有状态 server 需要自己实现句柄；
- 每次请求重复携带 capabilities（带宽/解析开销）；
- `sampling` 依赖者需改用 MRTR 重写；
- 生态里大量 2025 版 server 需要适配，12 个月弃用窗口偏紧。

**⑦ "又一个配置格式"的疲劳**
`【社区】`典型质疑："我们经历了 WSGI、OpenAPI、LSP，现在为一个配置文件欢呼？" 更实质的批评是：**每次统一都新增一层兼容层**，而兼容层本身成为新的技术债。反方观点同样成立：接口层标准化是生态成熟的必经之路。

### 5.3 尚未解决的三件事（对我们最有价值）

| 未解决 | 现状 | 我们的机会 |
|---|---|---|
| **统一信任模型** | A2A 有 JWS、AGNTCY 有 DID+VC、MCP 只有命名空间、Agent Plugins 完全没有 | 在自家 manifest 里做**统一的 trust 段**，把四套机制映射到同一套三态语义 |
| **统一权限模型** | 谁都没做（Agent Plugins v1.1 计划做） | 抢先定义 `permissions`（fs/net/exec/secrets），并与 MCP 工具注解联动 |
| **跨协议能力检索** | AI Catalog 只做"索引指针"，不做能力语义 | 用 OASF 分类法 + `representativeQueries` 建本地能力索引，做语义路由 |

### 5.4 监管变量

`【社区】` NIST 的 CAISI 于 2026-02 启动 **AI Agent Standards Initiative**（首个美国联邦层面的 agent 互操作与身份专项），并公开征询"agent 身份能否挂在 OAuth / OIDC / SPIFFE 上，还是必须另建"。同期 Okta、Cisco Duo、Proof（x401）分别从 IAM 侧切入 agent 身份。

> **对选型的含义**：身份层在 12–18 个月内可能被标准化重置。管理器应把身份做成**可插拔 provider**（DID / JWKS / OIDC / SPIFFE），不要硬编码任何一种。

## 6. 推荐原生支持的协议列表

### 6.1 分层建议

```
┌─ Tier 0  原生实现（自研解析 + 自研运行时）────────────────────┐
│  MCP 2026-07-28（+ 2025-06-18 兼容）                        │
│  Agent Skills（SKILL.md）                                   │
│  Agent Plugins 1.0（作为导入格式）                            │
│  自有 Plugin Manifest（本报告第 7 节）                        │
├─ Tier 1  原生支持（完整客户端实现）──────────────────────────┤
│  A2A 1.0.1（跟踪 1.1-rc：generation / SendLiveMessage）       │
│  AI Catalog / ARD（探测 + 解析 + 索引）                       │
├─ Tier 2  适配器（编译/桥接，不做完整实现）────────────────────┤
│  OpenAPI 3.x → MCP 工具（白名单 + 三元工具模式）              │
│  Arazzo 1.0 → 工作流工具                                     │
│  AGNTCY OASF/DIR → 导入能力分类与记录                         │
│  MCP Apps（按宿主能力渲染，沙箱 iframe）                       │
│  Claude Code plugin.json → 导入器                            │
├─ Tier 3  只读观察（不写代码，只做兼容预留）───────────────────┤
│  ANP / NANDA / agents.json / agents.txt / llms.txt           │
└──────────────────────────────────────────────────────────────┘
```

### 6.2 为什么不把 Agent Plugins 直接当自家清单

| 需求 | Agent Plugins 1.0 能否满足 | 缺口 |
|---|---|---|
| 一键发现 | 否（明确不做 registry / marketplace / discovery） | 无发现层 |
| 自动拉起 | 部分（有 `mcp.json`，但无 activation / health / lifecycle） | 无生命周期语义 |
| Agent 调度 | 否（无意图、无成本、无并发、无冲突声明） | 无路由元数据 |
| 安全治理 | 否（无权限、无信任、无密钥） | 三块全缺 |

**结论**：Agent Plugins 是"打包层"的好标准，正好是我们要**读取**的输入格式，而不是我们要**写出**的格式。自家清单应当在它的字段基础上做超集，并保持"能被降级导出为 Agent Plugins 目录"的能力。

### 6.3 明确不做的事

| 不做 | 原因 |
|---|---|
| 自研新传输协议 | 传输层已收敛到 stdio / Streamable HTTP / gRPC / HTTP，自研无生态 |
| 把 OpenAPI 全量暴露为工具 | 上下文爆炸 + 路由错误率上升；必须白名单 + 按需拉取 schema |
| 把 A2A Agent 包成 MCP Tool | 丢失 `INPUT_REQUIRED` / `AUTH_REQUIRED` 等人工介入点，语义坍塌 |
| 依赖单一 well-known 路径 | 规范路径本身在漂移（`mcp.json` vs `mcp/server-card`），必须探测列表 |
| 把"验签通过"当"可信" | 签名只证明密钥，不证明主体可信（A2A HS256 默认值就是反例） |
| 内嵌明文凭证 | 与所有主流规范冲突，且无法轮换 |

## 7. Plugin Manifest YAML Schema 草案

### 7.1 设计原则

| 原则 | 具体做法 |
|---|---|
| **YAML 写、JSON Schema 校验** | 作者面用 YAML（可注释、多行描述）；校验面用 JSON Schema 2020-12（YAML 解析后是同一棵树） |
| **只放指针，不复制内容** | `components` 里只放路径 / URL / 选择器；`SKILL.md`、`mcp.json`、`agent-card.json` 的**原生格式保持权威** |
| **最小必填 + 渐进增强** | 3 个必填（`apiVersion` / `kind` / `metadata.name`）；其余分段可选，加载器按存在与否降级 |
| **顶层 closed，扩展 open** | 未知顶层字段**报错**（避免拼写错误静默通过）；`extensions` 内按反向域名命名空间**开放** |
| **失败隔离** | 清单错 → 整包拒；组件错 → 只跳该组件并上报；运行期错 → 只降级该能力 |
| **权限默认拒绝** | `permissions` 缺省为"无权限"，不是"全权限" |
| **信任三态** | `signed` / `verified` / `trusted` 分离，禁止合并成一个 `trusted: true` |
| **可降级导出** | 能无损导出为 Agent Plugins 目录结构（`plugin.json` + `skills/` + `mcp.json`） |

### 7.3 字段 → 需求追溯表

| 需求 | 承载字段 | 说明 |
|---|---|---|
| **一键发现** | `metadata.id` / `publisher.domain` / `discovery.wellKnown` / `discovery.registries` / `discovery.mediaTypes` | 域名即身份锚；`mediaTypes` 让 AI Catalog 条目能正确声明类型 |
| **自动拉起** | `runtime.entrypoints` / `activation` / `health` / `lifecycle` / `resources` / `sandbox` | `activation: lazy` 是省资源的关键；`health.probe` 决定就绪判定方式 |
| **Agent 调度** | `routing.intents` / `triggers` / `concurrency` / `context` + `components.*.id` | `examples` 供语义匹配；`capabilityRefs` 供精确绑定；`destructive` 供审批门 |
| **安全治理** | `permissions` / `trust` / `sandbox` | 三者分离：能做什么、是否可信、在哪运行 |
| **可移植** | `components`（指针 + `format`） | 原生格式权威，清单只做索引与选择 |
| **可演进** | `apiVersion` / `compatibility` / `extensions` | 客户端按 `apiVersion` 判别语义，未知扩展忽略 |

### 7.4 加载与失败隔离规则（必须写进实现）

```
1. 读清单 → 校验 JSON Schema
   ├─ 失败 → 整包拒绝，报告具体 jsonPath（不允许"部分加载"）
   └─ 成功 ↓
2. 检查 apiVersion
   ├─ 未知主版本 → 拒绝并提示可升级的管理器版本
   └─ 已知 → 按 minor 做能力降级 ↓
3. 逐组件解析
   ├─ 组件路径越界（../、符号链接逃逸）→ 跳过该组件 + 安全告警
   ├─ 子格式校验失败（SKILL.md / mcp.json / agent-card.json）→ 跳过该组件
   └─ 成功 → 注册到能力索引 ↓
4. 权限求解
   ├─ 未授予的权限 → 该能力标记 unavailable（不是整包失败）
   └─ 全部授予 → 可激活 ↓
5. 信任求解（signed → verified → trusted 三级）
   ├─ 未签名 → 标记 self-asserted，默认要求显式确认
   ├─ 验签通过但 key 未 pin → 标记 verified-untrusted
   └─ key 来自已信任 JWKS/DID → 标记 trusted
6. 激活（按 activation 策略）→ health 通过后进入可调度池
```

**跨字段强约束（建议写进 schema 的 `allOf`）**

| 约束 | 理由 |
|---|---|
| `trust.signing.algorithm != "HS256"` | 对称签名对公开清单无意义 |
| `permissions` 中出现的每个 `hosts[]` 必须覆盖 `runtime.sandbox.network.egress` 的子集 | 否则沙箱与权限声明矛盾 |
| `routing.intents[].capabilityRefs` 必须能在 `components` 中解析到 | 防止悬空引用（JSON Schema 无法表达跨引用，由加载器/校验脚本检查） |
| `routing.intents[].destructive == true` ⇒ `requiresApproval == true` | 破坏性操作强制审批 |
| `components.openapi[].operations` 非空 | 禁止全量暴露 |
| `runtime.entrypoints[].transport == "sse"` ⇒ 必须提供 `streamable-http` 备选 | 兼容 ChatGPT / Codex 的限制 |
| `extensions` 的 key 必须匹配反向域名正则 | 防止命名空间抢占 |

### 7.5 与既有标准的关系（降级导出）

| 目标格式 | 导出映射 | 会丢失 |
|---|---|---|
| Agent Plugins 1.0 | `plugin.json`（`$schema` 改写）+ `skills/` + `mcp.json` | `routing` / `permissions` / `trust` / `runtime.lifecycle` |
| Claude Code plugin | `.claude-plugin/plugin.json` + `skills/` + `.mcp.json` + `commands/` | 同上，且 `userConfig` 需另映射 |
| MCP `server.json` | `name`（反向 DNS）+ `version` + `description` + `packages` / `remotes` | 技能、工作流、Agent、权限 |
| A2A Agent Card | `name`/`description`/`version`/`skills[]`（`id`+`name`+`description`+`tags`）/`capabilities` | 工具级 schema、权限、路由预算 |
| AI Catalog 条目 | `id`/`displayName`/`mediaType`/`url`/`tags`/`representativeQueries`（← `routing.intents[].examples`） | 除索引信息外全部 |

> **注意**：`representativeQueries` 与 `routing.intents[].examples` 语义高度重合，可**一次编写、两处使用**——这是本草案与 ARD 最自然的咬合点。

## 8. 协议适配层设计要点

### 8.1 总体架构（三平面）

```
┌────────────────────────── 管理器 ──────────────────────────┐
│                                                            │
│  ① 发现平面 Discovery                                       │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────────┐  │
│  │ AI Catalog│ │ Registry │ │ Well-known│ │ 本地扫描      │  │
│  │ 爬取      │ │ 查询      │ │ 探测列表  │ │ (~/.x/plugins)│ │
│  └────┬─────┘ └────┬─────┘ └────┬─────┘ └──────┬───────┘  │
│       └────────────┴────────────┴───────────────┘          │
│                          ↓ 去重 + 优先级 + 信任评分          │
│  ② 激活平面 Activation                                      │
│  解析清单 → 安装/定位 → 权限求解 → 信任求解 → 拉起 → 健康检查 │
│                          ↓ 注册                              │
│  ③ 调用平面 Invocation                                      │
│  ┌───────────────── 统一能力模型 Capability ──────────────┐  │
│  │ Tool │ Skill │ Agent │ Workflow │ Resource │ App       │  │
│  └───┬──────┬───────┬────────┬─────────┬────────┬─────────┘  │
│      ↓      ↓       ↓        ↓         ↓        ↓           │
│  ┌────────────────── 适配器 Adapters ────────────────────┐  │
│  │ MCP  │ A2A │ Skills │ OpenAPI │ Arazzo │ OASF │ Apps   │  │
│  └──────────────────────────────────────────────────────┘  │
│                          ↓                                  │
│  调度器 Router（意图匹配 → 能力选择 → 审批 → 执行 → 观测）    │
└────────────────────────────────────────────────────────────┘
```

### 8.2 发现平面：优先级与去重

**探测顺序（并行发起，按优先级合并）**

| 优先级 | 来源 | 说明 |
|---|---|---|
| P0 | 本地已安装清单 + 用户显式配置 | 最快、最可信 |
| P1 | `/.well-known/ai-catalog.json` | 一次拿到该域名下全部能力 |
| P2 | 各协议卡片探测列表（并行） | `/.well-known/mcp/server-card` → `/.well-known/mcp.json` → `/.well-known/agent-card.json` → `/.well-known/agent.json`（旧路径） |
| P3 | Registry 查询（MCP Registry、AGNTCY DIR、市场） | 只在用户搜索时触发，不做全量同步 |

**去重键**：`(publisher.domain, metadata.id)`；同一插件多来源时，按 `trust 等级 > 版本号 > 显式配置` 择一，并把其余来源记为 `mirrors`。

**缓存策略**：MCP 列表结果带 `ttlMs` / `cacheScope`（2026-07-28 起）——**必须遵守**，不要自定 TTL。`cacheScope: private` 的结果不得写入共享缓存。

**现实兜底**：因为 well-known 渗透率只有 1.7%–5.8%，必须有"**主动探测指纹**"兜底：默认路径 `/mcp` 上 POST 一个 `server/discover`（2026-07-28 起 MUST 实现），能应答即认定是 MCP server。这比猜路径可靠。

### 8.3 统一能力模型（Canonical Capability）

```yaml
Capability:
  id: "<pluginId>/<componentId>/<member>"      # 全局唯一，稳定
  kind: tool | skill | agent | workflow | resource | app
  display: { name, summary, examples[] }
  io:
    inputSchema: <JSON Schema 2020-12> | null  # A2A/skill 可能为 null
    outputSchema: <JSON Schema 2020-12> | null
    inputModes: [text/plain, application/json]
    outputModes: [...]
  semantics:
    readOnly: bool
    destructive: bool
    idempotent: bool
    openWorld: bool
    requiresApproval: bool
  execution:
    mode: sync | stream | task
    timeoutSeconds: int
    concurrencySafe: bool
  cost: { tokensHint, latencyHint, priceHint }
  provenance:
    protocol: mcp | a2a | skills | openapi | arazzo | oasf
    native: <原始描述对象，原样保留>
    adapterVersion: "1.4.0"
  trust: { signed, verified, trusted, publisher }
```

**关键设计：`provenance.native` 必须保留原始对象。** 任何归一化都是有损的，调试与审计只能靠原文。这是"不丢信息"的唯一办法。

### 8.4 四类适配器的职责边界

| 适配器 | 输入 | 输出 | 不可做的事 |
|---|---|---|---|
| **ToolAdapter（MCP）** | `tools/list` + `annotations` | `kind: tool` + 语义四元组 | 不得自动重试 `destructive`；不得跨 session 复用句柄（2026-07-28 无会话） |
| **ToolAdapter（OpenAPI）** | 白名单 `operationId` | 三元工具（list / get-schema / invoke） | 不得全量导入；不得凭空编造 `readOnly`（缺失即按 `destructive` 保守处理） |
| **AgentAdapter（A2A）** | `AgentCard` + `Task` 生命周期 | `kind: agent`，`mode: task` | **不得**把 Agent 伪装成同步工具；必须暴露 `INPUT_REQUIRED` / `AUTH_REQUIRED` 给上层 |
| **InstructionAdapter（Skills）** | `SKILL.md` frontmatter | `kind: skill`，只载入 name+description | 不得在 discovery 阶段读正文（破坏渐进披露，撑爆上下文） |
| **WorkflowAdapter（Arazzo / agents.json）** | flow / workflow 定义 | 单个 `kind: workflow` 能力 | 不得把每个 step 提升为独立工具（会产生大量近似重复工具） |
| **RegistryAdapter（OASF/DIR）** | OASF 记录 | 能力标签 + 分类 ID | 不得把 OASF 记录当可执行能力（它只是描述） |

### 8.5 错误模型统一

| 统一错误 | 来源映射 |
|---|---|
| `not_found` | MCP `-32601`；HTTP 404；A2A `REJECTED`（技能不存在） |
| `invalid_input` | MCP `-32602`（含 2026-07-28 起统一后的 resource-not-found）；HTTP 400/422 |
| `unauthorized` | MCP `-32021`（MissingRequiredClientCapability）；HTTP 401/403；A2A `AUTH_REQUIRED` |
| `rate_limited` | HTTP 429；`Retry-After` 必须透传 |
| `unavailable` | MCP `-32022`（UnsupportedProtocolVersion）/ 连接失败；A2A `FAILED`（基础设施类） |
| `interrupted` | A2A `CANCELED`；MCP 流中断（2026-07-28 **不再支持 SSE 重放**，必须换新 request id 重发） |
| `internal` | MCP `-32603`；HTTP 5xx |

**规则**：统一错误码用于路由与重试决策；**原始错误必须透传**给上层与日志（否则审计不可能）。

### 8.6 能力降级矩阵

| 缺失能力 | 降级策略 | 用户可见影响 |
|---|---|---|
| 无 `streaming` | 轮询 `GetTask` / `tasks/get` | 进度延迟，需设合理轮询间隔（建议 ≥2s 且指数退避） |
| 无 `pushNotifications` | 本地轮询 + 完成即回调 | 长任务无法即时感知 |
| 无 `outputSchema` | 文本结果 + 启发式解析 | 结构化程度下降，需 LLM 兜底 |
| 无 `inputSchema`（A2A skill） | 用 `examples` + `inputModes` 构造松散参数 | 参数错误率上升，必须保留人工确认 |
| 无 MCP Apps 支持 | 回退到 `structuredContent` + 文本 | UI 消失但功能保留 |
| 仅 SSE 传输 | 桥接为 Streamable HTTP | 需维护桥接进程；`Last-Event-ID` 语义丢失 |
| 无会话（2026-07-28） | 服务端句柄作为普通参数透传 | 需插件作者配合；老 server 需适配 |

### 8.7 上下文预算管理（决定调度质量）

| 手段 | 做法 | 依据 |
|---|---|---|
| 工具数量上限 | 单次注入 ≤ 40 个工具 | 主流宿主硬上限约 40 |
| 工具名长度 | ≤ 60 字符，加 `routing.context.toolNamePrefix` | 宿主限制 + 防冲突 |
| 两阶段注入 | 先给 name+summary（~20 token），命中后再拉完整 schema | 渐进披露 |
| 技能渐进披露 | 仅 name+description（~100 token/技能） | Agent Skills 规范 |
| 确定性排序 | 按 `metadata.id` 稳定排序，不打乱 | 提升 prompt cache 命中 |
| 缓存 | 遵守 `ttlMs`；`private` 不共享 | MCP 2026-07-28 |

### 8.8 安全设计（清单外的必做项）

| 威胁 | 具体表现 | 对策 |
|---|---|---|
| **工具描述投毒** | 描述里藏指令（"忽略之前的规则…"） | 描述按**不可信输入**处理：不拼接进系统提示，只作为结构化字段；对含命令式语句的描述做标记 |
| **rug pull** | 装的时候安全，`tools/list` 后来变了 | 用 `listChanged` 通知 + 工具定义哈希基线；变更即重新审批 |
| **签名伪造** | A2A 卡片默认 HS256；无算法白名单 | 强制非对称 + 显式算法白名单 |
| **密钥泄漏** | 清单内嵌 token；`isSecret` 未标 | 只允许 `refs`；header 中 `isSecret: true` 必须校验 |
| **路径逃逸** | `../`、符号链接指向包外 | 解析时 `realpath` 后必须仍在 `${PLUGIN_ROOT}` 内 |
| **UI 注入** | MCP App 的 HTML 执行任意脚本 | 沙箱 iframe + CSP `default-src 'none'` + 模板预审 |
| **供应链** | 依赖包被替换 | `integrity.digest` + SLSA provenance + 允许列表 registry |
| **权限蔓延** | 插件申请超出功能所需 | 权限按最小集审批；运行期越权即阻断并上报 |

### 8.9 观测

- MCP 2026-07-28 已文档化在 `_meta` 中传播 OTel 上下文（`traceparent` / `tracestate` / `baggage`）——**直接复用**，不要自造 trace 头。
- A2A 用 `Task.id` + `contextId` 做跨 hop 关联；`Task.generation` 做顺序校验。
- 每个能力调用记录：`capabilityId` / `protocol` / `adapterVersion` / `latency` / `outcome` / `nativeErrorCode`。
